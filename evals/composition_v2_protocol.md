# Composition v2 evaluation protocol

Comparative A/B/C status: **draft, not frozen and not executed**. This document defines a future experiment; it is not efficacy evidence. Exact model snapshot, host controls, held-out fixture files and enforceable accounting remain unresolved. The [development behavior suite](../results/composition_v2/behavior-suite/README.md) has its own execution record and remaining gates; development runs cannot establish comparative efficacy. Preserve all historical protocols, templates and results unchanged; new records belong under `results/composition_v2/`.

## Questions and separation

1. **A — architect plus handoff:** Does adding v2 architecture and the shared contract to one fixed director improve implemented outcomes within the same total budget?
2. **B — review:** Does a fresh independent rendered reviewer improve those artifacts more than budget-matched builder self-review?
3. **C — confirmation, later:** After revisions, does the frozen complete combination outperform the pinned incumbent on three additional fresh briefs?

A measures the architect-plus-handoff bundle, not isolated wording or director brands. B measures review independence with tools and budget held constant. C is a separate 12-build experiment, not a relabeling of pilot artifacts. No measured builds are authorized or recorded by writing these definitions.

## Development and activation gates

`composition_v2_cases.json` defines eight development probes. They are excluded from efficacy scores and may be used for tuning. Their prepared fixtures, fault controls, original prompts and actual evidence are archived in the linked development record; held-out pilot fixtures remain unbuilt. Run each future probe in a fresh context from a temporary full-folder skill installation outside the repository, with repository research and historical results unavailable to the task. Verify relative references and manifest resolution from that installed copy. The recorded development environment used task instructions rather than an OS-enforced read barrier; its full global skill roster and model alias limit generalization.

For each probe perform (1) an explicit invocation of `creative-frontend-architect` and (2) an unprompted selection run using the exact ordinary user prompt and the intended surrounding installed-skill roster. Save roster names, versions/hashes, relevant descriptions and ambient instructions; record actual selected skills and reads. Do not feed the agent the probe's expectations or the suite. A description-only classifier, injected wrapper or simulated transcript is not a real activation test. A selected skill must actually be read; a missing selection and a read without subsequent behavior are distinct outcomes. Isolate competing director bodies after selection and record any contamination; do not present a contaminated run as a clean activation pass.

All critical assertions must pass with trace plus relevant runtime evidence before packaging/activation is accepted. Missing evidence is `unverified`, not pass. An intentionally unavailable preview passes the *truthful fallback* assertion when disclosed, while rendered quality remains unverified. The settings probe additionally tests reviewer detection/correction of seeded defects; do not conflate that with an efficacy trial.

## Pilot cases and contamination control

Pilot Q/W/S briefs in the cases file use new content and task structures: repair dispatch, a seed-library membership launch, and a tidal archive. They are reserved from development. Build and pin new minimal fixture directories with complete local assets/data and deterministic state controls; do not recycle a historical solution, project page or a development implementation. Shared unstyled framework scaffolding is allowed if documented and hashed. The pilot briefs are public protocol definitions, not secrets; held-out means no development builds, tuning or selection on their outputs. Any pilot case used for tuning loses that designation and must be replaced before freezing. Authors who read the suite cannot serve as fresh build agents with that conversation context.

## Conditions and run matrix

| Stage | Condition | Work | Count |
| --- | --- | --- | --- |
| A | `A_director` | Fixed director with its ordinary implementation workflow, ordinary self-checks | 3 briefs × 2 repetitions = 6 initial builds |
| A | `A_architect` | Same director plus v2 adapter, architect and shared handoff; ordinary self-checks | 3 briefs × 2 repetitions = 6 initial builds |
| B | `B_self` | Builder reviews/corrects each A_architect artifact | 6 continuations |
| B | `B_independent` | Fresh reviewer diagnoses; builder corrects each identical A_architect artifact | 6 continuations |
| C, later | `C_incumbent`, `C_combination` | Pinned incumbent versus complete frozen candidate | 3 additional briefs × 2 repetitions × 2 conditions = 12 fresh builds |

A has **12 initial builds**. B has **12 continuations**, all six A_architect artifacts forked twice, including broken or timed-out starts. B is not 12 new builds. Preserve the original A artifacts before continuation. Selection is unconditional; no best-of, successful-build filtering, or aesthetic selection.

For A use Anthropic as the implementation control, pinning its actual source and ordinary workflow before freeze. The v2 adapter resolves `CFA_ANTHROPIC_SOURCE` when set, otherwise the host-advertised source, verifies the expected pin/hash, and applies its attributed scoped adaptation; it must not claim execution of the full upstream workflow. This adaptation is part of the measured bundle. A missing source or hash mismatch uses `builtin-fallback` and is an exposure failure, not validated upstream compatibility. The `A_director` condition must not load v2 architecture, contract or rendered-review modules. The `A_architect` condition loads director adapter and architecture/contract but **does not load or invoke the new independent review intervention**. Record this experiment-only stage restriction in the condition prompt. Neither condition gets an independent reviewer. Ordinary self-checks remain allowed in both; do not inject the new review rubric into just one condition. Adapter and handoff context count toward treatment cost. Disable specialist skill modules for this pilot in both conditions to isolate the bundle; ordinary package documentation remains available under identical tool policy. Runtime specialist work in later experiments must be fully counted.

Pin exact condition wrapper text in the freeze record: control identifies the pinned director and asks it to implement the case with its ordinary workflow; treatment invokes the installed candidate through architecture/implementation with the experiment-only review restriction. Both receive identical original brief, fixture, assets, environment, commands, budget notice and ordinary self-check permission. The study runner supplies condition modules explicitly in A; natural activation is tested separately above.

Match exact model snapshot, effort, sampling when exposed, context limit, agent/host version, hardware/browser version, fixture hashes, sources, available tools, network/package access, asset rights and total budget within every comparison. Agent spawning capability is available in both arms but its use follows the intervention: B_self uses the builder for review, B_independent uses a fresh reviewer. No other assisting agents are allowed during A/B. Do not silently substitute a source or model mid-block. A model alias without a reproducible snapshot is a disclosed limitation requiring a predeclared freeze decision, not an exact snapshot claim.

Randomize condition order within the six case/repetition blocks using a saved seed and save the complete schedule before starting. Use clean checkouts and fresh agent contexts for each A run. Serialize browser/performance measurements on the same device without competing builds or renders. Within B, fork identical filesystem and builder context checkpoints before either branch; keep ports, workspaces and evidence separate. If the host cannot fork/checkpoint context, resolve and freeze a symmetric reconstruction method before running, including its context cost, and disclose that limitation. Do not give the independent reviewer builder messages, self-assessment, scores or the other branch's findings.

## Proposed budgets, stopping and failure accounting

These are concrete **proposals**, not active controls. Freeze exact enforceable settings and commands first. Limits cover all director, builder, specialist (if later permitted), reviewer, correction, read/context-replay and ordinary verification work. Paid/cached input and repeated context are not free.

| Stage, each run | Proposed total token cap | Proposed elapsed cap | Allocation |
| --- | ---: | ---: | --- |
| A initial build, either arm | 600,000 aggregate input + output tokens | 45 minutes | Shared pool for design, implementation and ordinary checks |
| B continuation, either arm | 250,000 additional aggregate tokens | 20 minutes | 100,000 tokens / 8 minutes for all reviews/rechecks; 150,000 / 12 minutes for all corrections |
| C complete build, either arm | 850,000 aggregate tokens | 65 minutes | Freeze matched phase allocation after pilot; same total in both conditions |

Budget feasibility basis: one unscored development smoke build on Astra with high effort reported 304,091 input tokens plus 11,227 output tokens, totaling **315,318 aggregate tokens**, in the final `turn.completed` usage event of `work/v2-implementation/forward-build-trace.jsonl` (implementation-workspace evidence, not a distributed runtime dependency). Cached input (260,480) is already included in input, and reasoning output (590) is already included in output; neither subset is added again. That simple HTML build exceeds the earlier draft A proposal of 120,000 under this protocol's aggregate semantics. The revised proposals allow development-informed headroom; a single smoke run does not establish sufficiency for the held-out briefs or prove token-cap enforcement. Confirm budget feasibility and enforcement before freezing, or select the consistently applied wall-clock-primary mode below. Elapsed limits and outcome/promotion thresholds are unchanged. No efficacy experiment has been frozen or completed.

The subsequent development suite exposes a larger budget feasibility gap: D3 explicit used **2,141,470 parent input-plus-output tokens in 1,177.35 seconds**, before unknown descendant usage. These uncontrolled development runs do not revise the proposed caps or establish cost comparisons. Isolate ambient workflow skills and validate symmetric enforceable accounting before selecting and freezing budgets.

B allocations are cumulative across at most two correction-and-recheck cycles, not per-cycle grants. Start with an initial review, then correction/recheck, then at most one further correction/recheck; unused review time/tokens cannot expand corrections or vice versa. All builder checkpoint loading/replay counts in correction allocation; reviewer context loading counts in review allocation. Incumbent C may spend its equal budget using its documented workflow; predeclare allocation and avoid granting the candidate free review time.

A run terminates on the first hard elapsed or enforceable token cap, explicit agent completion, or unrecoverable failure. Start the clock at first agent dispatch; include source reads, waiting for tools, installs, builds and intervention browser work. Stop agent work and dependent commands at termination; no grace-period repairs. Capture the last artifact and terminal trace. Freeze a 120-second cap per ordinary shell command, with 300 seconds for dependency installation or production builds, and a 60-second preview readiness cap. A command timeout is logged and may be retried only within the remaining overall budget. A started preview server can remain alive for assessment but cannot perform agent edits after the cutoff.

If aggregate token enforcement is unavailable, choose and document a wall-clock-only primary budget **before freeze**, keep the identical elapsed cap in both arms, and record unavailable token usage as null with reason. Do not claim token matching from estimates. Select the same accounting mode for the entire experiment. Save per-agent and per-phase consumption; total duration is elapsed time, while summed agent-active seconds is a separate quantity. Do not add parallel durations and call the result elapsed time. Report B incremental cost separately and link to A; combined A+B cost must not double-count the A start.

Failed builds, unavailable previews, timeouts, source fallbacks and contaminated runs remain in the assigned-condition outcome table. A source fallback does not count as having loaded the assigned director. Environment failures are flagged separately, never silently deleted or replaced; any authorized rerun has a new run ID and preserves the original. Report planned denominator (six pairs), completed pairs, valid-exposure pairs and reasons separately. Missing/unverified outcomes cannot earn a win or satisfy promotion. If a fixture itself is defective, record a protocol deviation, invalidate affected comparisons and refreeze a replacement before new runs; do not repair one arm's fixture in place.

## Review intervention and outcome assessment

B starts from every A_architect artifact and accepted contract. Both B branches receive the same original brief, contract, running URL, state controls, evidence locations and review checklist. The self-review branch retains the builder identity/context; the independent reviewer starts fresh with those inputs only. It may inspect source to diagnose observed faults. Record identity, fresh-context evidence and actual browser evidence independently: `review_mode=independent` does not imply browser verification. If an independent reviewer cannot be created, record fallback to self-review, keep assigned condition and actual mode distinct, and do not treat it as a valid independence comparison.

The checklist operates the primary task at desktop 1440×900 and mobile 390×844; exercises empty/loading/error/success when applicable; tests keyboard and focus; checks reduced motion and motion/offscreen/hidden work when applicable. Capture the failing state and reproduction, not only a beauty screenshot. Findings contain severity, expected/observed behavior, viewport/state, reproduction, evidence and smallest correction. Label design preferences separately from defects; permitted brand conventions are not failures just because a module dislikes them. Intentional art-direction changes return to the same design owner. Rechecks cover changed behavior and the primary flow. A remaining blocking defect after the cycle cap is incomplete.

A separate outcome assessor receives anonymized artifacts, the original brief, functional acceptance conditions and identical live state controls, not intervention notes, module labels, builder claims or costs. The assessor must not be either intervention reviewer or builder. Randomize pair order/labels with a saved seed and keep the mapping outside assessor inputs. Avoid exposing `.design`/run metadata in the served artifact; preserve them in archived originals. Identity cues that cannot be concealed are disclosed. Assess A artifacts before B changes and each B final artifact; use the same assessor procedure for C.

Score each dimension 0–4 with evidence: **task completion, mobile usability, visual coherence, brief specificity, accessibility**. Anchors: 0 absent/blocked; 1 major failures; 2 usable with material defects; 3 complete with only minor defects; 4 complete and particularly strong on the stated brief. Accessibility 4 requires exercised keyboard/focus, readable content and relevant reduced-motion behavior, not a claim of comprehensive conformance. Missing observation is null, not 0 and not pass. No single aggregate quality score may mask broken flows. Also record primary-flow pass/fail/unverified and counts of deduplicated actionable defects by severity: blocking (prevents required task/content), major (materially impairs required use with workaround), minor (localized impairment). Count one underlying defect once; preferences do not count.

For each matched pair record left/right/tie overall preference with rationale tied to the brief, individual dimension scores and task failures. A prettier but broken result cannot receive a favorable adoption verdict. Use all outcomes and preserve before/after screenshot, motion and flow evidence. Obtain the same scripted states/time windows from every artifact; do not cherry-pick hero views. Performance captures use identical viewport/device/choreography and report actual frame/CPU observations where available. Narrative smoothness claims without measurement remain unverified. Outcome assessment/capture work is not build budget, but is identically bounded and separately accounted: propose 15 minutes per artifact plus five minutes per matched decision, with no assessor code fixes or feedback to builders.

## Proposed internal decision rules

These are conservative product decisions, not significance tests; twelve pilot builds cannot justify broad superiority claims.

- No newly introduced primary-flow, accessibility or shared-renderer failure; no fabricated loading or verification claims.
- A: at least four of six paired comparisons favor the architect bundle, no brief loses both repetitions, and task failures are reported alongside preference. Ties are not wins; incomplete pairs cannot be omitted to shrink the denominator.
- B: fewer total remaining actionable defects than matched self-review across all six pairs, no new blocking defect, and report severity and per-brief/per-pair outcomes so minor-defect totals cannot hide major regressions. If all starts are clean, defect-reduction value is inconclusive. Missing rendered outcomes prevent this gate from passing.
- A component consuming equal budget without measured benefit stays experimental or is reduced. Development compliance or longer plans alone are not benefit.

After any revision, freeze a candidate and separately authored **three additional fresh Q/W/S briefs** with new fixtures, two repetitions per condition (12 C builds). Do not reuse pilot or development briefs, solutions or scores. Pin the exact incumbent release and its workflow, candidate modules and all budgets/tools/assessment rules before C. Proposed useful advantage: at least four of six pairs favor the combination, or a strictly lower total remaining actionable-defect count with no worsened blocking/major count and no more than two preference losses. All required flows must pass; no new major-defect pattern (the same introduced major failure on two or more runs), fabricated evidence or shared-renderer regression is allowed. These exact thresholds are draft until frozen. Promotion cannot use cases that tuned the candidate. Broader repeated evidence is needed for public “substantially better” claims; limited adoption may be justified only for supported surfaces.

- [ ] Tools, network/package policy, no-extra-agent policy, working directories, seeds/order and artifact checkpoints fixed.

## Run metadata conventions

Copy `run_metadata_v2_template.json` per run. Null means unavailable/not yet recorded, with an entry in `accounting_unavailable_reasons` or `notes` as appropriate; empty arrays mean no recorded entries, not verified absence. This is ordinary metadata, not JSON Schema. Never fill a value with a pipe-separated enum/example.

- `condition_id` is assigned condition; `actual_workflow`, `fallbacks`, `review_mode` and `verification_status` record observed execution. Review modes: `independent`, `self-review`, `none`. Verification: `verified`, `partial`, `unverified`; `browser_status`: `available-used`, `available-unused`, `unavailable`, `failed`. These vocabularies are documentation, not template values.
- `loaded_files` entries contain `role`, `path` (actual resolved path), `sha256`, `load_status`, `expected_revision`, `actual_revision`, `loaded_at`, `trace_path`, `trace_event_id` and `read_scope`. Unknown revisions are null. Hash the bytes actually read; a full-file hash plus exact read scope is acceptable for partial reads. Keep expected pinned hashes separately; record match/mismatch/unknown in `source_resolution`. A listed path, registry URL or manifest entry is not proof of a read. Include entrypoint, references, adapters, director source and any specialist source actually read.
- `director_adapter_revision` records adapter commit or content hash; `design_director_loaded` records actual source identity or `builtin-fallback`. `source_resolution` entries identify expected source/revision/hash, actual source/revision/hash, resolution result and read evidence. Record unavailable sources without invented hashes.
- `agent_accounting` entries contain `agent_id`, `role`, `parent_agent_id`, `model_snapshot`, `phase`, `input_tokens`, `output_tokens`, `cached_input_tokens`, `reasoning_tokens`, `active_duration_seconds`, `cost_usd`, `usage_trace_path` and `unavailable_reason`. Record all participating agents, even if every numerical usage field is null. State whether reasoning/cached tokens are included in provider totals; never add already-included tokens twice.
- `total_budget` records allocated caps and enforcement mode, not actual consumption. `total_tokens` aggregates input plus output without double counting cached/reasoning subsets. If any contributing agent usage is unavailable, aggregate total is null; report known partial usage separately. `total_cost_usd` likewise stays null when incomplete; do not imply zero cost. Preserve per-stage cost for A/B and separately record assessor/capture accounting.
- `reviewer_identity`, `reviewer_context_isolation`, `review_cycles` and `browser_status` are separate observations. Each cycle records reviewer identity, findings path, correction diff, recheck trace and unresolved blockers. `activation` records invocation mode, surrounding roster, selected skills and observed read trace.
- `terminal_status` records completed/timeout/build-failed/tool-failed/interrupted as applicable, with cutoff reason, command timeouts and last artifact preserved. Status does not replace task/quality assessment. `artifacts` links trace, checkpoint/diff, original brief, contract, captures, measurements, findings and blind outcome records.
