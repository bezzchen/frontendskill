# Design contract — Notification preferences

Help repair co-op members control routine email around their repair commitments. Use a calm, compact form headed “Notification preferences,” followed by “Choose which emails you receive and when.” Director: `builtin-fallback` (explicitly selected source unavailable; evidence in work-log.md). The user brief is the authority for existing conventions; application files were not inspected.

| Area | Decision |
| --- | --- |
| Identity and layout | Fixed navy `#123347` text on cream `#FAF7F0`; preserve native checkboxes, time inputs and buttons. Reuse the application font; system sans-serif if unavailable. Heading 24px, labels/body 16px, helper text 14px, line height 1.5. Single column, maximum width 40rem, 24px section spacing, 8px label/help spacing; 16px side padding on narrow screens. No illustrations, decorative cards or new color tokens. |
| Email reminders | Native checkbox labeled “Email reminders.” Helper: “Reminders about your upcoming repair bookings.” Initialize from saved preferences; preserve the existing reminder schedule. |
| Weekly digest | Independent native checkbox labeled “Weekly digest.” Helper: “A weekly summary of co-op news and repair opportunities.” Preserve the existing delivery day. Neither checkbox enables the other. |
| Quiet hours | Native checkbox “Use quiet hours,” then labeled native time inputs “From” and “Until.” Retain but disable time inputs when unchecked. Show the member’s saved time zone by name. If no saved interval exists, propose 21:00–08:00 without enabling it automatically. Overnight intervals are valid; equal start/end times show “Choose different start and end times.” Intent: defer both selected email types until quiet hours end; changing quiet hours never subscribes the member to email. |
| Save feedback | Explicit native “Save preferences” button. Start disabled until a change exists. During submission show “Saving…” and disable the form to prevent conflicting edits. On confirmed success, show persistent inline “Preferences saved.” and reset the changed state. On failure, retain edits, restore controls and show “Couldn’t save preferences. Try again.” Clear stale success feedback on the next edit. Never indicate success before persistence is confirmed. |
| Accessibility and narrow screens | Visible, associated labels; group quiet hours with a legend and connect help/errors to their controls. Preserve native keyboard behavior and visible focus. Time fields may sit together on wide screens; stack on narrow screens without horizontal scrolling. Announce saving/success politely and failures as alerts; put focus on the first invalid field after submission. Use text, not color alone, for feedback. |

Register: **Q — Quiet / Operate**, because this is a practical settings task. Adopt existing native controls and ordinary HTML/CSS layout; no effect catalog search is needed. Browser-native controls own interaction and focus; no graphical engine, animation or continuous work is proposed. Reduced-motion users receive the same static experience. If stored settings cannot load, show “Couldn’t load preferences. Try again.” with a retry action and keep saving unavailable rather than displaying invented saved values.

Acceptance for later implementation: all four requested areas are present; saved values load correctly; the two email choices remain independent; quiet-hour validation, overnight scheduling and time-zone handling work; failed saves preserve edits; successful saves survive reload; keyboard, announcement, focus, contrast and narrow-screen behavior are verified. These are design requirements, not observed behavior. Scheduling support, saved time-zone availability, actual typography and all rendered/accessibility checks remain unverified in this plan-only task.
