## 2. Register: W (Expressive) — spectacle weighed and declined

The brief signals a narrative ("three-act", "story advances", "coordinated stages"), so I explicitly weighed **S (Spectacle)**: a realtime graphical system (WebGL/shader diagram, particle field, procedural type) as the section's core. **Declined.** The content *is* typography, diagrams and project media; a realtime system would compete with them, require a canvas + engine + offscreen-pause machinery, and cut against "the rest of the site should remain ordinary semantic UI." **W** fits: motion serves one signature idea — the drawn SVG path as the story's spine that binds the three acts and then hands off to the ordinary page.

## 5. Decision: CSS-native choreography, zero dependencies, section stays a **server component**

**Core idea:** author the case study once as plain semantic HTML in its complete, resting state. Layer the pinned layout *and* the choreography as one CSS enhancement block that only exists when it can run:

```css
@media screen and (prefers-reduced-motion: no-preference) {
  @supports (animation-timeline: view()) { /* pinned layout + keyframes live only here */ }
}
```

Consequences that satisfy the brief:
- **Reduced-motion users, Firefox stable, Safari < 26, print, and no-JS all receive the identical fallback: the plain three-act article in flow** — same content, no choreography. One fallback, not two.
- **Zero client JS**: `app/page.jsx` remains a server page; the only client component on the site is still `SettingsPanel`. No hydration flash, no CLS from the section (media queries resolve before first paint).
- **No engine touches these transforms** — ownership is unambiguous (one owner per concern). If the alternative is ever chosen, CSS must not animate the same properties.

**Assumption (explicit):** Firefox-stable parity is *not* a hard requirement — Firefox users get a complete, static case study. **Switch trigger:** if the owner requires parity, or the director's choreography needs physics/cross-element coupling `animation-range` can't express, switch the engine to Motion 13 inside a single `"use client"` component with the *same DOM and same fallback*, decided before implementation begins — never both.

### DOM (semantic, unchanged across modes)

```
<article id="project-1" aria-labelledby="case-study-title">   ← satisfies ProjectGrid's first anchor
  <div class="wrapper">            ← enhanced: block-size 300svh; view-timeline: --story block
    <div class="stage">            ← enhanced: position sticky; top 0; block-size 100svh; display grid
      <ol class="rail">…3 act markers…</ol>
      <svg aria-hidden><path pathLength="1" …/></svg>   ← the drawn spine
      <section class="act">…Act I: h3, copy, diagram, media…</section>
      <section class="act">…Act II…</section>
      <section class="act">…Act III…</section>
    </div>
  </div>
</article>
```

### Timeline mechanics (the load-bearing details)

- Named **view timeline on the wrapper**; every animated node is its descendant, so lookup succeeds across ancestors and **no `timeline-scope` is needed** (sidesteps Chrome 138's removal of `timeline-scope: all`).
- **`animation-range: contain 0% contain 100%` maps exactly onto the pinned interval**: for a subject taller than the viewport, `contain` runs from "wrapper top reaches viewport top" (pin starts) to "wrapper bottom reaches viewport bottom" (pin ends, sticky releases). Acts get sub-ranges (e.g. `contain 0%–36%`, `32%–68%`, `64%–100%`, overlaps tuned by the director); the first act's entrance can use `entry`, giving a natural on-ramp; the last act ends visible so the release into "Account settings" is a plain scroll — **no `position: fixed`, no scroll hijack, no snapping.**
- **Path draw:** `<path pathLength="1">` normalises geometry; base `stroke-dasharray: 1; stroke-dashoffset: 0` (complete = fallback); enhanced keyframes `1 → 0` over `contain`. `stroke-dashoffset` is the one non-compositor property in the design — keep it to a single moderate path, `vector-effect: non-scaling-stroke`.
- Acts overlap via `grid-area: 1 / 1` only in enhanced mode; keyframes animate `opacity` + `translate`/`scale` (compositor) and step `visibility: hidden` for out-of-range acts so no invisible element stays focusable.
- Footguns to encode: write `animation-timeline` and `animation-range` **after** the `animation` shorthand (it resets them); use `animation-duration: auto` explicitly; clip with `overflow: clip`, never `hidden`, anywhere above the stage (a scroll container kills sticky); use `svh` units.
- **constraint 1 (offscreen/hidden pause):** there is *no* ambient or continuous animation — all motion is scroll-linked, so nothing runs while idle or offscreen and there is no ticker to pause. If the director later wants any idle motion or video, it must be paused offscreen (`IntersectionObserver`) and on `visibilitychange`; I recommend adding none.

## 7. Verification plan — actual conditions, not proxies (constraint 2)

Run against `next dev` with the Playwright/Browser tools available in this environment; Chromium exercises the enhanced path, Firefox the fallback.
1. **Hold:** sample ≥ 10 scroll positions; while the wrapper spans the viewport, `stage.getBoundingClientRect().top === 0 (±1px)`; before pin `> 0`; after release `< 0` **and** the settings section's top moves 1:1 with further scroll (natural release).
2. **Staging & path:** at progress ≈ 0.05/0.5/0.95 assert computed `opacity`/`translate` of acts I/II/III; assert `getComputedStyle(path).strokeDashoffset` decreases monotonically to `0` at release.
3. **Reduced motion:** `emulateMedia({ reducedMotion: 'reduce' })` → no element in the section has an active `animation-timeline`; wrapper height ≈ content height (not `300svh`); every act visible in flow; path complete.
4. **Unsupported browser (Firefox):** same assertions as #3.
5. **Idle cost:** confirm the section registers no `scroll`/`rAF`/interval handlers and produces no long tasks while offscreen — recording that there is nothing to pause is itself the check.
6. **SSR/no-JS:** `curl` the HTML contains all three acts' text; JS disabled renders identically.
7. **Layout/a11y:** `scrollWidth` never exceeds the viewport at 360/768/1280px; heading order h2 → h3×3; `aria-labelledby`; decorative SVG hidden; media has alt text; anchor `#project-1` lands at progress 0.
8. **Real Safari 26** smoke test of sticky + view timeline (BCD says supported; I did not observe it in this session — treat as unverified until run).

**Build order:** data + fallback article (complete on its own) → SVG spine + enhanced CSS layer → director staging pass → verification matrix. Roughly one focused day.
