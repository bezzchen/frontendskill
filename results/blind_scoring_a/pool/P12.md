## 2. Register: Q (Quiet / Operate)

A settings form is an operate surface; the brief asks for polish and interaction quality, not a concept or a spectacle. I weighed the spectacle register explicitly and decline it: no brief signal (unforgettable / experimental / immersive), and a realtime graphical core would work against the job (speed, trust, accuracy). The unused `ConstellationData.js` is an obvious invitation to a particle/canvas backdrop; declined as out of scope and register-breaking. W (one signature idea) was also considered; the only "signature" here is the save-state choreography, which is micro-motion, so Q holds. Consequence: micro-motion only, zero new runtime dependencies by default.

**Animation engine.** `motion` 13.2.0 (same package as framer-motion): full `motion` component 34 kB; `m` + `LazyMotion` ≈ 4.6 kB initial plus `domAnimation` (+15 kB) for exit animations; `motion/mini` 2.3 kB without `AnimatePresence`. Motions this page needs: switch thumb slide, focus/border color, error reveal/hide, button state swap, status fade, sticky-bar enter/exit. Every one is a single-property transition or entry/exit of a mounted node; Tailwind 4.3.3 ships `starting:` (`@starting-style`), `transition-discrete`, `user-invalid:`, `motion-reduce:`, `pointer-coarse:`, `forced-colors:` and `animate-spin` (all confirmed present in the installed dist). The only thing `motion` would add is exit animation of *unmounted* React nodes, which I avoid by keeping error/status slots mounted and toggling state. **Decline.**

Also declined: react-hook-form/zod (five fields; one 40-line shared validator plus native constraints), zxcvbn (hundreds of kB; a requirements checklist is clearer and more accessible than a score), toast libraries (one `role="status"` region per form), Radix/RAC for a single switch (the WAI-ARIA APG switch pattern lists a native-checkbox example, and React Aria ships that exact approach). **Proposed files** (not created):

**Structural decisions (defaults chosen; flag if you want otherwise):**

1. **Two forms, not one.** Profile + Notifications share one "Save changes"; Password is its own form with "Update password". Reasons: different auth semantics (current password required), password managers key on isolated forms with `autocomplete="current-password"` / `"new-password"`, no validating an optional empty password on every profile save, and each form gets its own pending/saved state. A shared `SaveBar` keeps one visual language.
2. **Toggles save with the form**, not autosave. One Save affordance already exists; autosaving toggles beside an explicit Save is two mental models. Alternative if preferred: per-row autosave with `useOptimistic` and an inline row status.
3. **Save via React 19 form actions + Next Server Actions.** `const [state, action, isPending] = useActionState(saveProfile, initial)`; `useFormStatus` in the `SubmitButton` child. Works without JS (native POST, server re-renders errors). Handled caveat from the React docs: uncontrolled fields reset after a successful action, so fields are controlled (needed for dirty tracking anyway) and seeded from the action's returned `values`. Persistence is an explicit stub with a seam for a real store.
4. **One validation module** used by client (instant feedback) and action (authoritative). Policy: validate on blur; once a field has shown an error, re-validate on change; on submit validate all, move focus to the first invalid field, render a summary linked to fields. Native constraints (`type=email`, `required`, `minLength`) stay so `user-invalid:` styling works before hydration.
5. **State model per form:** `idle → dirty → submitting → saved → idle`, with `invalid` / `error` branches. `dirty` = compare current values to last-saved snapshot. `saved` holds ~2.5 s, then returns to idle, or immediately on the next edit. One `role="status"` (polite) region per form; the message carries a time ("Saved · 14:32") so consecutive saves re-announce; a failed submit uses `role="alert"`.

**Tokens (mechanism is mine; values are the director's).** Keep the five existing variables; add `--line-strong` (≥ 3:1 on surface in both schemes), `--accent`, `--accent-contrast`, `--success`, `--danger`, `--ring`; register them with `@theme inline` so `bg-surface`, `border-line-strong`, `text-muted` exist (existing `bg-[var(--surface)]` keeps working); dark values go in the existing media block. Constraints for the director: switch "on" track ≥ 3:1 against surface; error/success never color-only (icon + text); `forced-colors:` handled on the switch (border/outline, not fills).

**Font.** `next/font` is the mechanism if the director wants a specific face; the Google loader downloads at build time and `next build` fails offline (`NextFontError`), so vendor a woff2 via `next/font/local` with `variable` + `@theme inline --font-sans`. Default recommendation: Tailwind's system `font-sans` stack (no requests, no CLS). Director's call.

**Layout.** Settings becomes a stack of cards (`bg-surface border-line rounded-xl`), each a `<section aria-labelledby>` with an `h3` and a one-line description; at `lg` a two-column card grid (description | fields) collapsing to one column. Name/email side by side at `sm+`. Notifications is a `<fieldset><legend>` of rows (label, description, switch); the component supports N rows — row content is a content decision (e.g. email notifications, product updates, security alerts).

## 5. Interaction and motion spec (all CSS, 120–200 ms; 250 ms for the bar; `motion-reduce:` drops transforms and keeps opacity or goes instant)

- **Field focus:** border → `line-strong`, 2 px ring with offset on `focus-visible`; color transition 150 ms.
- **Error reveal:** slot always mounted; `grid-rows-[0fr]→[1fr]` + opacity; errors reach AT via `aria-describedby` + focus move, not per-field live regions.
- **Switch:** native checkbox with `appearance-none`, track 44×24 px minimum, thumb `translate-x` 150 ms ease-out, track color 150 ms; whole row remains the click target; `pointer-fine:` only micro-detail: thumb widens slightly on `:active`.
- **Submit button:** fixed min-width; cross-fade idle → spinner + "Saving…" → check + "Saved". Spinner is Tailwind `animate-spin`, mounted only while pending and unmounted otherwise (bounded by the request; not ambient). `aria-disabled` + guard during pending instead of `disabled`, so focus is not lost.
- **Sticky SaveBar:** `sticky bottom-0` inside the form, `pb-[env(safe-area-inset-bottom)]` (Tailwind has no safe-area utility), translucent surface; enters with `starting:` translate/opacity when dirty (`transition-discrete` for the display flip), reverses on clean; `scroll-padding-bottom` on the form equal to bar height so a focused field is never obscured (WCAG 2.4.11).
- **Status:** fades in with the timestamp, fades out on return to idle.
- **Invalid submit:** focus move + summary only. No shake (a W-register gesture that irritates on repeat).
- **Password:** show/hide button with `aria-pressed` and `aria-controls`; requirements checklist (min 12 chars, not equal to name/email, etc.) updating live with a single summarized `aria-live` count to avoid chatter; no confirm field (WCAG 3.3.7 redundant entry — show/hide replaces it).

constraint check: this design has **no ambient or continuous animation**; the only loop is the pending spinner, bounded and unmounted at rest, with no library ticker involved. `<ViewTransition>` is available on 16.2 only via `experimental.viewTransition` (vendored React `19.3.0-canary…` carries it; flag defaults false) and is not needed here, so the project stays config-free.
