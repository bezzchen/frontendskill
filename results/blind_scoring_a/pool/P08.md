## Recommended architecture: one shared WebGL2 overlay canvas, raw GL, progressive enhancement

**Shape of it**

- **DOM stays exactly as it is.** `ProjectGrid` remains a server component; the cards remain the truth for SEO, a11y, layout, and responsiveness. The only grid edit is incidental (e.g., swapping the gradient div for a real `<img>` when assets exist — the `data-project-media` hook is already the perfect seam).
- **One new client component**, e.g. `components/ProjectMediaFX.jsx` (`"use client"`), rendered as a *sibling* of the grid in `app/page.jsx`. On mount it: checks `prefers-reduced-motion` and WebGL2 support (bail silently on either), finds all `[data-project-media]` elements, creates **a single `position: fixed`, full-viewport `<canvas>`** with `pointer-events: none` and `aria-hidden="true"`, and draws one textured quad per card at that card's `getBoundingClientRect()` (pixel-space orthographic projection). Only once the first GL frame has rendered does it visually hand off (hide the DOM media via `visibility`), so failure at any point leaves the current site untouched.
- **Framework-free GL core** in `lib/refraction/` — a small renderer module (context, one shader program, N quads, uniforms) plus a shaders module. React only mounts/unmounts and forwards events; the GL code never touches React. This keeps the interesting code testable and portable, and keeps the client-component surface tiny.
- **Interaction wiring:** pointer position and per-card hover/focus state feed shader uniforms (refraction = noise/normal-driven UV displacement around the pointer, plus chromatic aberration — the standard "liquid glass" recipe). `focus-visible` on a card link drives the same uniform as hover, so keyboard users get parity. Click on a card triggers a per-quad transition uniform (time-driven warp/dissolve that can escape the card bounds, since the canvas is viewport-sized). Because navigation is a same-page hash change, nothing interrupts the animation today; when a real detail route arrives, the same architecture supports either "play, then `router.push`" or persisting the canvas in `layout.jsx` across the route change.
- **Perf discipline:** render-on-demand rAF loop (runs only while the pointer is active over the grid or a transition is settling, then cancels), rect cache refreshed on scroll/resize, DPR capped at 2, offscreen cards skipped.

**New surface area:** two small files plus one line in `page.jsx` and possibly one attribute in `ProjectGrid.jsx`. Zero new dependencies. Zero changes to server-rendered HTML semantics.

## Why this beats the nearest alternatives

1. **Per-card canvases** (a canvas inside each card) — superficially simpler (no rect syncing), but: 8 separate WebGL contexts sits right at typical browser context limits (~8–16) and duplicates program/texture state 8×; a per-card canvas is clipped to the card, so the "dramatic" open transition can't grow beyond its bounds without overflow hacks; and it drags 8 component instances through React lifecycle instead of one. The only cost the shared canvas pays is syncing 8 rects, which is trivial.
2. **three.js / react-three-fiber (or OGL)** — the workload is *textured 2D quads + one fragment shader*. No scene graph, no camera math, no model loading — i.e., none of what those libraries are for. three.js adds ~150 KB and R3F adds a second reconciler tree coupled to React 19/Next 16 versions; OGL is lighter but still a dependency whose abstractions go mostly unused. Crucially, the genuinely hard part — the shader — is identical code either way, so the library buys almost nothing here. Raw WebGL2 for this scope is a few hundred lines you own outright. (If the team later refuses to own GL boilerplate, OGL is the acceptable fallback; three.js/R3F is not warranted.)
3. **SVG/CSS filters** (`feTurbulence` + `feDisplacementMap`) — genuinely the least code, but it cannot hit the stated bar: displacement maps don't follow the pointer without regenerating turbulence per frame, which stutters on the main thread; Safari's SVG-filter performance is poor; and a "shader-like" open transition is out of reach. "Least unnecessary complexity" is bounded below by the quality requirement, so this fails on necessity, not on taste.
4. **Rasterizing whole cards into textures** (the classic "liquid page" demo approach) — explicitly violates the brief: text must stay selectable, accessible, real DOM. Distorting only the media is what makes the single-overlay approach clean.
5. **WebGPU** — adds nothing for a 2D refraction effect and worsens the fallback story; WebGL2 is the right floor.

**Constraints honored by construction:** SEO and a11y are untouched because the canvas is decorative (`aria-hidden`, `pointer-events: none`) and all interaction stays on the real links; responsiveness is inherited because quads follow DOM rects, so Tailwind's `md:grid-cols-2` keeps owning layout; reduced-motion and no-WebGL users get today's site bit-for-bit.

**Decision points to settle at implementation time:** (a) texture source while media is still a CSS gradient — either rasterize the gradient once or generate it procedurally in the shader (procedural is cleaner until real images land); (b) whether the open transition blocks navigation once a real route exists (recommend: play ~400–600 ms, then push).

result: Recommended a zero-dependency single shared WebGL2 overlay canvas (raw GL in `lib/refraction/`, one small client component syncing quads to the existing `data-project-media` DOM rects, progressive enhancement with reduced-motion/no-GL bailout) over per-card canvases, three.js/R3F/OGL, SVG filters, and card rasterization — no implementation, per instructions.
