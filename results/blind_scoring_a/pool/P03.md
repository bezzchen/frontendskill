## Register

**W (Expressive)** with one bounded graphical surface. I weighed **S (Spectacle)** explicitly because "high-end", "dramatic", "shader-like" all signal it — and decline it: the brief scopes the realtime system to the image layer only and requires the page's structure (text, layout, links, a11y, SEO) to remain DOM. The GL layer is a skin on one element type, not the structural core. That is W by definition.

## Recommendation: one shared WebGL2 canvas that skins the DOM images

**DOM (unchanged in kind):** `ProjectGrid` stays a Server Component. The gradient div becomes a real `<img>` (alt, intrinsic dimensions, lazy, srcset) marked with a data attribute. The `<img>` remains the layout box, the accessibility node, the indexed image, and — once loaded — the texture source. Nothing about layout, links, or responsive behavior moves into GL.

**One new client component** (`RefractionLayer`, mounted once in `app/layout.jsx`) owning every GL concern:

1. A single fixed, viewport-sized `<canvas aria-hidden pointer-events:none>` with one WebGL2 context. Links keep hover, focus, click, and open-in-new-tab exactly as before.
2. A registry of `[data-gl-image]` elements (scanned on mount and on `usePathname()` change), rects read from `getBoundingClientRect()` — the DOM is the sole source of truth for position/size; GL only reads.
3. Textures uploaded from the already-decoded `<img>` (no second fetch; same-origin or `crossOrigin`). Each image stays visible until its first GL frame is drawn, then gets `opacity: 0` — not `visibility: hidden`, which would remove it from the accessibility tree.
4. Two passes per frame: (a) one small viewport-space **flowmap** ping-pong (e.g. 256²) accumulating pointer velocity with dissipation, shared by all quads; (b) one image program drawing only the quads currently intersecting the viewport, displacing UVs from the flowmap with per-channel offsets (dispersion) plus a highlight from the flowmap gradient — the "refraction" read. Amplitudes, dispersion, and timing are uniforms for the design director; nothing here sets the look.
5. **Open transition, same machinery:** intercept a plain left-click on a card link (keyboard Enter dispatches `click` too), tween that quad's rect uniforms from its DOM rect to the viewport rect while a progress uniform drives the dramatic effect, then `router.push(href)` and hand off. The canvas must live in the root layout precisely so it survives the client navigation.
6. **Pause policy (constraint 1), structural not bolted on:** demand rendering — the rAF loop exists only while pointer energy > ε, a transition is active, or the flowmap hasn't dissipated; hard stop on `document.hidden` and when zero images intersect the viewport. There is no library ticker to police because there is no library.
7. **Fallbacks:** no WebGL2 or context lost → plain DOM images (WebGL2 is at 95.73% full support per caniuse data); `prefers-reduced-motion` → no distortion, open is a short CSS fade; `(hover: none)` → no hover effect, transition still runs.

**Cost:** zero new runtime dependencies, zero config changes, one client module of a few hundred lines including shaders. One owner per concern: GL owns the image pixels and the quad transform; the DOM owns everything else.

## Why this beats the nearest alternatives

- **Per-image canvases (any catalog component):** 8 GL contexts now (browsers cap around 16 and silently evict the oldest as the grid grows), 8 loops to pause, 8 program compiles and duplicate ripple sims — and decisively, a card-sized canvas cannot expand to the viewport, so the open transition needs a second mechanism (portal a canvas to `body`, re-upload the texture). Two architectures for one feature. None of the pointer-reactive candidates pause offscreen either.
- **react-three-fiber + drei `<View>`:** the same shape as my recommendation, but three + fiber + drei (20 deps) for one 2D program, an SSR boundary, a second frameloop to configure, and three volatile APIs to inspect on every upgrade. Justified only if the site grows real 3D; it's a portfolio grid and a settings form.
- **OGL as a thin substrate:** honest accounting — it saves roughly the context/program/texture boilerplate plus the flowmap ping-pong, for one dependency and an API surface to inspect. It doesn't change the architecture at all. Take it only if the team would rather not own FBO code; I wouldn't as first choice for something this small.
- **SVG `feDisplacementMap` on the `<img>` (zero-dependency DOM option):** filters re-rasterize on the CPU per attribute change (`feTurbulence` especially); 8 animated filters won't hold 60 fps on integrated GPUs, per-channel refraction/specular needs stacked filters, and there is no shader transition. Fails "high-end" on both asks.
- **View Transitions for "open":** elegant and now config-free in Next 16.3 (I'd verify on the installed 16.2.12), but CSS-only, so not "shader-like", and it captures pointer events while running. If it's ever used for headings later, the image must have exactly one owner — never a `view-transition-name` *and* a GL quad.
- **Canvas in `page.jsx` instead of the root layout:** unmounts on navigation and cuts the transition mid-flight.
- **GSAP/Motion for the tween:** one 700 ms progress value is a five-line easing; an engine is unnecessary here, and two engines must never own the quad transform.
