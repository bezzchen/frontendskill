# Architecture proposal — three-act scroll case study

## 1. What the repo is

- Next 16.2.12 (App Router, Turbopack default), React 19.2.8, Tailwind 4.3.3, **plain JS** (`jsconfig.json`, `.jsx`). No `next.config`, no ESLint, no TS.
- Zero animation dependencies; `node_modules` absent. Repo-wide grep: no `sticky`, `overflow`, `animation`, `transition`, or `prefers-reduced-motion` rules anywhere — this section will set the site's motion conventions.
- `app/page.jsx` is a server component: header → `<ProjectGrid />` (server) → "Account settings" `<SettingsPanel />` (client). `main` is `max-w-6xl px-6 space-y-24`, no overflow rules (sticky-safe).
- `ProjectGrid` links to `#project-1…#project-8`; **no such anchors exist**. The case study should be `id="project-1"` so the first card resolves.
- Design tokens: `--background/--foreground/--muted/--surface/--line`, light/dark via `prefers-color-scheme`.
- `components/ConstellationData.js` (500 synthetic nodes) is **never imported**. Flagging it as a trap: binding 500 SVG nodes to scroll would be 500 style recalcs per frame. Not used by this design.
- Next 16 removed automatic `scroll-behavior: smooth`; `#project-1` jumps are instant unless `data-scroll-behavior="smooth"` is added to `<html>` (either works with the design).

## 2. Register: W (Expressive / Persuade) — spectacle weighed and declined

The brief's own verbs are narrative ones: hold, stage, track, draw, release, "rest of the site ordinary." Motion serves one signature idea (a three-act story with one drawn line as its spine). I explicitly considered S (spectacle): a realtime graphical core (shader/particles/3D) would (a) compete with the case-study content it is supposed to serve, (b) introduce a continuous render loop that must then be pause-managed, (c) add a substrate to a site whose other surfaces (grid, settings form) are register Q. Interaction here only scrubs a deterministic timeline; nothing "materially changes a system." **Declined.** The grid and settings stay untouched, ordinary semantic React.

- The three hard requirements — page-level hold, clean release, reduced-motion content parity — appear in **no** catalog component. That is the "nothing fits, build custom" outcome.

## 5. Mechanics — one owner per concern

**Hold and release (layout, no JS).** `.track { height: calc((var(--scrub, 3) + 1) * 100svh) }` contains `.panel { position: sticky; top: 0; height: 100svh }`. The panel pins when its top reaches the viewport top and simply scrolls away when the track ends — release is structural, no pin-spacer, no measured heights, no jump. Ancestors must never get `overflow: hidden` (use `clip` if clipping is ever needed).

**Progress (JS, sole writer).** Per frame: `p = clamp(-track.top / (track.height - panel.height), 0, 1)` from one `getBoundingClientRect()`; written as `--p` on the section root only when it changes by >1e-4; `data-act` (1/2/3 from `timeline.js` thresholds) updated only on change. IntersectionObserver on the track (`rootMargin: 50% 0px`) attaches/detaches the passive `scroll`/`resize` listeners, so **outside the section zero code runs per scroll**; inside, at most one rAF is pending at a time and none while idle. There is no ticker, no lerp loop — constraint 1 is satisfied structurally, and `document.hidden` has nothing to pause (still verified, see section 8). No React state on the hot path; the component never re-renders on scroll.

**Interpolation (CSS, sole consumer of `--p`).** Every staged element is a pure function of `--p` via inline windows, so reverse scrolling and deep-linking are deterministic and testable:

```css
@media (prefers-reduced-motion: no-preference) {
  [data-story="on"] .stage {
    --kin:  clamp((var(--p) - var(--in)) * var(--inv), 0, 1);
    --kout: clamp((var(--p) - var(--exit, 2)) * var(--exitInv, 1), 0, 1);
    --k: min(var(--kin), 1 - var(--kout));
    opacity: var(--k);
    transform: translate3d(0, calc((1 - var(--k)) * var(--rise, 1.5rem)), 0);
    will-change: opacity, transform;   /* ≤ ~15 elements, section-scoped */
  }
}
```
Multiplication by a precomputed `--inv` (1/span) avoids `calc()` division edge cases. No CSS transitions by default (true scrub); if wheel stepping looks choppy, an ≤80 ms opacity transition is allowed — it self-terminates, unlike a JS smoothing loop, which stays banned.

**Timeline (progress space 0–1, in `timeline.js`, tunable).** Entry plateau 0–0.04 → Act 1: heading 0.04–0.12, diagram fragment 0.08–0.18, media 0.12–0.22, exit 0.30–0.36 → Act 2: 0.36/0.40/0.44 in, exit 0.62–0.68 → Act 3: 0.68/0.72/0.76 in, holds → settle plateau 0.94–1.0 → release. Typography, diagram, and media enter as three offset beats per act — the "coordinated stages." Default 300svh of scrub (`--scrub: 3`).

**SVG path draw (CSS from `--p`, one JS measurement).** The spine path visits the three act nodes in order and draws 0.04→0.94: `stroke-dasharray: var(--len); stroke-dashoffset: calc(var(--len) * (1 - clamp((var(--p) - 0.04) * 1.111, 0, 1)))`. `--len` is `path.getTotalLength()` measured **once** on mount (user units are invariant under viewBox scaling), written **unitless**. Deliberately *not* relying on `pathLength="1"`: it has no MDN BCD entry, WebKit/Blink historically ignored it for dash scaling, and Safari today rescales px-unit dashes under page zoom (Motion issue #3301; fix there is unitless values). Also avoid `vector-effect: non-scaling-stroke` on this path — its interaction with `stroke-dash*` is an unresolved SVG WG issue with Firefox bugs on record. Node arc-length fractions should land near 0.10 / 0.42 / 0.74 so the drawing tip reaches each node as its act enters (director/implementer tune `d`).

**Static mode is the default, choreography is opt-in — two independent gates.** All choreography CSS is scoped under `[data-story="on"]` **and** `@media (prefers-reduced-motion: no-preference)`. The hook sets `data-story="on"` only after computing `--p`/`--len`/`data-act` (no snap) and only when `matchMedia('(prefers-reduced-motion: reduce)')` is false; it listens for `change` and deactivates live. Consequences: without JS, before hydration, or with reduced motion, the section renders as plain document flow — header, complete diagram figure, three stacked acts, media, footer — track `height: auto`, panel `position: static`, all opacity 1, path fully drawn. Same DOM, same data → "same content" by construction, not by a parallel implementation. Known trade-off: deep-linking to `#project-1` shows the static layout for the hydration window, then snaps to the `--p` state; acceptable, and a pre-hydration inline script can remove it later if wanted.

**Semantics and a11y.** `section > header(h2) + ol.acts > li(h3, p) + figure(svg role="img" + figcaption) + figure(media) + footer(CTA)`; reading order = act order; screen readers get the whole story regardless of scroll (opacity, never `display`/`visibility`). **No focusable elements inside the pinned panel** — the single CTA lives in the in-flow footer, so nothing tabs into invisible content. If the director later insists on links inside acts, gate non-current acts with `inert` via `data-act` (React 19 supports it), accepting that it also hides them from AT. Path stroke and staged elements use the existing tokens; the director may add one accent for the spine.

**Ownership map.** Progress: `useScrollProgress` (only writer of `--p`, `data-act`, `--len`, `data-story`). Visual mapping: the CSS module (only reader of `--p`; JS never writes `opacity`/`transform`). Timeline numbers: `timeline.js`. Copy/media: `caseStudyData.js`. Visual thesis, type, palette, diagram style, pacing feel: **the design director** — none is installed; the implementer should load exactly one (`frontend-design` is available) for that pass. This proposal fixes slots and mechanics only.

## 6. Layout and fit budget

Pinned panel is a two-column grid ≥ `md` (typography left; diagram + media overlapping right), rows below; acts overlap in one grid cell (`grid-area: 1/1`) only under `[data-story="on"]`. Panel content must fit `100svh` at 360×640 (checked in QA); if it can't, the fallback is the static layout under one `max-width` media query — the same CSS the reduced-motion path already uses. Panel height is `svh` on purpose: `dvh` would change the scrub span mid-scroll and jitter; the transparent strip below the panel when mobile toolbars collapse is invisible against the page background. Full-bleed vs `max-w-6xl` is the director's call; sticky works either way.

## 7. Decisions I am defaulting (owner may override)

1. Case study = Project 01, `id="project-1"`, placed between the grid and Account settings.
2. Copy and media are placeholders in the grid's existing gradient convention (`data-project-media`), swappable for `next/image` (note Next 16's changed image defaults: `qualities [75]`, `localPatterns` for query-string sources).
3. Mobile stays pinned; static fallback is one media query away.
4. 300svh scrub with entry/settle plateaus.
5. If the site later adopts Motion site-wide, this section migrates to `useScroll` and the `--p` contract makes that a local change — never two engines on one transform.

## 8. Verification plan (actual conditions, Playwright at implementation)

1. Hold: at 50% of the track, panel `top ≈ 0` and `--p ≈ 0.5`. 2. Stages: computed opacity of each act at p = 0.1/0.5/0.9 matches the timeline, forward **and** backward. 3. Path: `stroke-dashoffset ≈ len·(1−draw(p))`, unitless; 0 at p ≥ 0.94. 4. Release: scroll past the track; `scrollY` monotonic, document height constant, settings `h2` arrives with no jump. 5. Reduced motion: `page.emulateMedia({ reducedMotion: 'reduce' })` + reload → panel `static`, all opacity 1, offset 0, `innerText` identical to the choreographed render; toggling mid-session deactivates. 6. Idle cost: with the section offscreen, instrumented rAF + listener counters stay at 0 while scrolling elsewhere; no rAF pending when `document.hidden`. 7. Fit: `panel.scrollHeight ≤ clientHeight` at 360×640, 390×844, 768×1024, 1440×900. 8. `next build` clean, no hydration warnings, `#project-1` deep link lands, keyboard PageDown/Space progress the story, light and dark both legible.
