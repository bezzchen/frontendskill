Dependencies aren't installed yet (no `node_modules`) — worth noting for the implementation phase, but I have everything needed to assess the code. Here's what I found and what I propose.

## Current state

**Stack:** Next.js 16.2 (App Router), React 19, Tailwind CSS v4 (CSS-first config, no `tailwind.config`), plain JSX, no TypeScript, no animation/form/component libraries. Design tokens live in `app/globals.css` (`--background`, `--foreground`, `--muted`, `--surface`, `--line`) with light/dark via `prefers-color-scheme`. The page is a warm-neutral portfolio; `ProjectGrid` uses bordered `--surface` cards.

**The settings panel** (`components/SettingsPanel.jsx`, 69 lines) is a single client component with concrete gaps:

- **No save lifecycle.** Submit sets `saved=true` permanently — it still says "Saved" after you edit again. No pending state, no dirty tracking (button is always active even with no changes), no error path.
- **No validation.** Email accepts anything; name can be empty; password has no rules.
- **Accessibility bugs.** The password input has no label (placeholder only). Group headings are `<h2>` nested under the page's `<h2 id="settings-title">`, flattening the hierarchy — they should be `<h3>`.
- **Visual flatness.** Native unstyled checkbox for "toggles" (singular, despite the plural intent), default browser focus rings, no hover/active/disabled button states, sections float without the card treatment the rest of the page uses.
- **Mobile.** No sticky affordance for save, checkbox touch target is tiny, and inputs don't guard against iOS auto-zoom (needs 16px font) or declare `autocomplete` hints.

## Proposed architecture

Decompose the monolith into a small settings module — no form library (react-hook-form is overkill for 6 fields) and **no animation library** (reasoning below):

```
components/settings/
  SettingsPanel.jsx     — "use client" orchestrator: state, validation, save machine
  SettingsSection.jsx   — card shell (title, description, children), matches ProjectGrid cards
  TextField.jsx         — label + input + hint/error with full ARIA wiring
  PasswordField.jsx     — TextField variant: show/hide toggle + strength meter
  ToggleRow.jsx         — accessible switch row (native checkbox, styled track/thumb)
  SaveBar.jsx           — save button + status; inline on desktop, sticky bar on mobile
lib/settings-validation.js — pure validators + password strength scorer (unit-testable)
```

`app/page.jsx` stays put except the heading-level fix; `app/globals.css` gains tokens and keyframes.

**State model** (plain React, one `useReducer`-lite shape in SettingsPanel):
- `values` + `savedValues` (last committed) → `isDirty` by shallow compare. Editing after a save naturally re-arms the button and clears "Saved".
- `status: 'idle' | 'saving' | 'saved' | 'error'` — a real save lifecycle. Save goes through one async `saveSettings(values)` stub (~700ms simulated latency) that is the seam for a real API; the `error` branch is fully rendered so a rejecting endpoint degrades gracefully.
- `errors` + `touched`: validate on blur after first touch ("reward early, punish late" — a field turns valid instantly while typing, only turns invalid on blur/submit); on submit, validate everything, focus the first invalid field, announce via the live region.
- Notifications become a config-driven array of 3 real toggles (e.g. email notifications, project inquiries, weekly digest) so "toggles" is plural and the section earns its card.
- Password is change-optional: empty means "no change" and is valid; non-empty enforces min length + basic strength. Cleared from state after successful save.

## Interaction and visual direction

- **Tokens:** add `--accent` (the page currently has zero accent — I'd pick a restrained moss/olive that suits the warm greys, tuned for AA in both schemes), `--danger`, `--ring`, `--accent-contrast`. Everything else reuses existing tokens so the panel feels native to the site.
- **Sections as cards:** `--surface` + `--line` border + rounded-xl, matching ProjectGrid; header row with title (h3) and one-line muted description; toggle rows separated by `divide-y`.
- **Switches:** visually-hidden native checkbox driving a styled 44x24 track with a sliding thumb (CSS transition). Full keyboard/AT support for free, `:focus-visible` ring on the track, whole row is the tap target.
- **Inputs:** consistent height, hover border shift, 2px `--accent` outline ring on `focus-visible` (outline-based: no layout shift, honors forced-colors), `aria-invalid` + `--danger` border + error text that reveals via the CSS `grid-template-rows: 0fr -> 1fr` technique (animates height without JS measurement).
- **Password:** show/hide button with proper `aria-label` state, 4-segment strength meter + text hint ("Weak/Fair/Good/Strong") tied to the scorer, `autocomplete="new-password"`.
- **Save state:** fixed-width button that morphs Idle ("Save changes", disabled+muted when clean) → Saving (inline spinner) → Saved (SVG check drawn via stroke-dashoffset, auto-reverts after ~2s) → Error (retry affordance + message). Status mirrored to the existing `aria-live="polite"` region. A small "Unsaved changes" dot/text appears when dirty.
- **Motion policy:** all micro-interactions are CSS transitions/keyframes gated with `motion-safe:` / a global `prefers-reduced-motion` guard.

**Why no animation library:** everything above — switch thumb, error reveal, button morph, check draw, sticky-bar slide — is achievable with CSS + a timeout ref. Framer Motion would add ~35kB gzipped to buy layout-animation conveniences this page doesn't need. Zero new runtime deps keeps it production-lean; if the app later grows dialogs/toasts, that's the point to revisit.

## Mobile plan

- Inputs at 16px font (blocks iOS auto-zoom), `autocomplete` on all fields, `inputmode`/`type` correctness.
- Touch targets ≥44px (toggle rows, buttons); card padding steps down at small widths.
- **Sticky save bar** slides up from the bottom only when `isDirty` on small screens (backdrop-blur, top border, `safe-area-inset-bottom` padding, form gets bottom padding so nothing is obscured); on `sm:` and up it renders inline at the form's end.

## Accessibility commitments

Labeled password field; `aria-describedby` chains for hint+error; `aria-invalid`; focus management to first invalid field on failed submit; native checkbox semantics for switches; visible focus rings everywhere; h1→h2→h3 hierarchy fixed; AA contrast for accent/muted/danger in both color schemes; reduced motion honored; live-region announcements for saving/saved/error.
