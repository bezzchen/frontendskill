## 4. Architecture

`app/page.jsx` keeps importing `SettingsPanel`; the panel becomes a thin shell composing two independent forms. Proposed files (all under the repo root above):

- `components/SettingsPanel.jsx` — layout shell: section card, header with one-line description, the two forms.
- `components/settings/ProfileForm.jsx` (`"use client"`) — `useActionState(saveProfile, initialState)`; Name and Email fields; Notifications `<fieldset>`; dirty tracking; the action bar.
- `components/settings/PasswordForm.jsx` (`"use client"`) — its own `useActionState(changePassword, …)`; current, new, confirm; show/hide; strength hint; inline submit.
- `components/settings/primitives.jsx` — `TextField`, `SwitchField`, `FieldMessage`, `SubmitButton` (reads `useFormStatus`, so it must render as a child of the form), `StatusRegion`.
- `lib/settings.js` — pure `validateProfile`, `validatePassword`, `passwordStrength`, plus simulated async actions `saveProfile(prev, formData)` and `changePassword(prev, formData)` with ~600ms latency and a deterministic failure path (email domain `fail.test` returns a server-style error) so the error UI is reachable and verifiable.
- `lib/settings.test.js` — `node --test` unit tests for the validators.
- `app/globals.css` — add an `@theme inline` block mapping the existing variables to Tailwind tokens (`--color-surface: var(--surface)` and so on, so `ProjectGrid` and the header are untouched) plus new `--color-accent`, `--color-danger`, `--color-success`, `--ease-out-quart`, and duration tokens.
- `app/page.jsx` — only the settings section wrapper changes (width and an `id`), nothing above it.
- `.gitignore` — `node_modules`, `.next`, `.env*`, `.DS_Store`.

**Why two forms.** Changing a display name should never require or touch credentials; a password change is a security action with its own pending state, its own confirmation copy, and fields that *should* clear on success. The page-level "Save changes" governs profile and notifications only. (Single-form alternative in section 9.)

**Profile form state.** `useActionState` returns `{ status: 'idle' | 'success' | 'error', values, fieldErrors, formError, savedAt }`. Inputs stay uncontrolled; `dirty` is derived by one `onInput` handler on the `<form>` that compares `new FormData(form)` against `state.values`. Submit → action re-validates with the same validators used client-side → latency → returns saved `values`. Because the inputs read `defaultValue` from `state.values`, React 19's automatic post-action reset of uncontrolled fields lands on the newly saved values rather than snapping back to stale defaults. That claim gets verified under the actual condition (edit, save, confirm the field keeps the new value without a flash); the fallback if it flickers is `onSubmit` + `startTransition(() => formAction(formData))`, which skips the auto-reset.

**Save state machine.** idle → (submit, only if dirty and not pending) → pending (button shows spinner + "Saving…", `aria-disabled`) → success (label crossfades to check + "Saved", held 2s, then idle; status region: "Changes saved"; dirty resets) or error (field errors revealed under their fields, focus moves to the first invalid field, status region: "Couldn't save. Fix the highlighted fields."; a `formError` from the simulated server renders an inline banner above the bar and the button stays enabled for retry). When clean, the button is `aria-disabled` (still focusable — no `disabled` focus trap) and pressing it announces "No changes to save".

**Switch.** `<input type="checkbox" role="switch" name="…">` inside a `<label>` row, `appearance-none` track with a pseudo-element thumb, `checked:` for the on state, `focus-visible:` ring, `forced-colors:` border so Windows High Contrast does not erase it, `pointer-coarse:` padding for a 44px target. The whole row is the label and therefore the tap target. Proposed group: "Email notifications", "Weekly digest", "Security alerts" in a `<fieldset><legend>`; optionally the digest goes `inert` and dimmed when email is off (section 9).

**Password form.** `autocomplete="current-password"` / `"new-password"` (both new and confirm); a `<button type="button" aria-pressed aria-controls>` show/hide; strength via `passwordStrength()` scored 0–4 on length and variety, exposed as hint text through `aria-describedby` with the segment bar `aria-hidden`. Enforced rules: minimum 8 characters, not equal to the current password, confirm matches; composition is guidance, not a gate. On success the auto-reset clears the fields (desired here) and the status region says "Password updated".

**Layout thesis (director owns final).** On `md+` each group is a two-column row — left: `<h3>` plus a one-line description; right: controls — collapsing to one column below. The section sits on a `surface` card with hairline dividers, and the action bar is the card footer. This needs the section widened from `max-w-2xl` to about `max-w-4xl` in `page.jsx`. Palette stays the existing warm neutrals plus one accent (on-state, focus ring, success) and one danger hue, both validated in light and dark at 4.5:1 for text and 3:1 for UI components.

## 6. Accessibility contract

- Every input has a visible `<label for>`, including all three password fields; `autocomplete`, `spellcheck="false"` and `autocapitalize="off"` on email.
- Errors: `aria-invalid="true"` and `aria-describedby` pointing at the message (and hint) id; on failed submit focus moves to the first invalid field, with `scroll-margin-bottom` equal to the sticky bar height so it is never hidden beneath it.
- One `role="status"` region per form; no per-message `role="alert"`, so three errors produce one announcement plus a focus move.
- Heading outline repaired: `h2` Account settings → `h3` Profile / Notifications / Password (or `<legend>`s).
- Native switch role, Space toggles, Enter submits from any text field; visible focus rings in both schemes; `forced-colors:` handling on the switch and the segment bar.
- Color is never the sole indicator: error text with icon, switch state exposed through `role="switch"`, strength conveyed by text.
- Inputs use 16px text on mobile to prevent iOS focus-zoom.

## 7. Mobile behavior

Single column, labels above fields, 44px minimum control height. The profile form's action bar becomes `sticky bottom-0` below `md` with a translucent surface, hairline top border, and `padding-bottom: env(safe-area-inset-bottom)`; it shows "Unsaved changes · Reset" when dirty and the save status otherwise, so a user deep in a long page always knows whether a save is pending. `sticky` (not `fixed`) keeps the bar inside the form's scroll context and behaves predictably when the on-screen keyboard opens. The password form is short, so its button stays inline — two stacked sticky bars would be worse than none.

## 9. Decision points for you

1. **Two forms (recommended) vs one.** One form is possible: password fields become optional-as-a-group (blank = unchanged; any filled = all required and matching). It loses independent pending/success states and clears nothing on save.
2. **Two-column settings layout** (requires widening the section in `page.jsx`) vs keeping the current single column at `max-w-2xl`.
3. **Notification toggles**: keep the single toggle, three independent toggles, or three with the master/dependent (`inert`) relationship.
4. **Repo hygiene**: add `.gitignore` and the `node --test` file (recommended, zero deps).
5. **`components/ConstellationData.js`**: leave untouched (default) or delete as dead code.
