## What the repository is

- Next.js 16 App Router + React 19 + Tailwind 4, JavaScript only, zero runtime deps beyond React/Next (`package.json` has no animation/3D libraries).
- `<REPO>` is a **server component**: 8 plain `<a href="#project-N">` cards, each with a heading, summary text, and a media slot that is currently a **CSS-gradient placeholder `div`** (not a real `<img>`) already tagged `data-project-media`.
- The only client component is `SettingsPanel.jsx`. `ConstellationData.js` is unused by any page. There are no project detail routes — "opening" a project is a dead hash link today.

Three repo facts shape the decision: the DOM is already exactly the semantic baseline the ask wants to preserve; the media slots are placeholders (real images will arrive later, so the effect layer must bind to a contract, not to `<img>` specifics — `data-project-media` is that contract); and "open" has no destination yet.

## Recommended architecture

**One shared WebGL2 canvas overlay with DOM-rect-synced planes, mounted as a single non-SSR client island; the DOM stays canonical and untouched.**

Concretely:

1. **`ProjectGrid.jsx` stays a server component, byte-for-byte semantic.** Cards remain real links; media slots keep `data-project-media` (plus a stable `data-media-id` when wired). No `use client` spreads into existing components — so text, headings, links, SEO, and responsive layout are untouched by construction, not by discipline.
2. **One new client island** (e.g. `components/gl/DistortionLayer.jsx`, loaded via `next/dynamic` with `ssr: false`) renders a single `position: fixed`, `pointer-events: none`, `aria-hidden="true"` `<canvas>` spanning the viewport. It mounts nothing when WebGL is unavailable, on `prefers-reduced-motion: reduce`, or on coarse pointers (`(hover: hover) and (pointer: fine)` gate) — the page is already complete without it, so the fallback tier is "no effect," the cheapest possible one.
3. **Framework-free GL core** in plain modules (renderer: context/programs/textures/DPR/context-loss; sync: rect measurement via ResizeObserver + per-frame scroll offset, IntersectionObserver culling). React owns lifecycle only; no per-frame React state or re-renders.
4. **Sync model**: each `[data-project-media]` element gets one textured quad drawn at exactly its screen rect. Today the texture is the placeholder gradient (rasterized once, or generated in-shader from computed colors); when real `<img>`s land, the upload path switches to the element's `currentSrc` after decode — so responsive `srcset` still picks resolution.
5. **Interaction**: pointer events are delegated on the grid (the DOM keeps receiving all events since the canvas is `pointer-events: none`), feeding a uniforms object (pointer UV, velocity, hover progress with lerp/spring). A single RAF renders **only while any plane is "hot"**; idle grid = zero GPU work and native-crisp DOM images (the plane fades in over the image on enter, first frame undistorted, so there is no fidelity mismatch at rest).
6. **Hover effect** = fragment shader on that plane (lens refraction/displacement, chromatic aberration; if the spec calls for persistent liquid trails, one ping-pong flowmap FBO). Effect internals are implementation, not architecture.
7. **Open transition** = a progress uniform on the clicked card's plane, which — because the canvas is page-wide — can **expand beyond the card's box** toward a hero/fullscreen composition. Per-card canvases physically cannot do this without re-parenting hacks; this is the requirement that most strongly selects the shared-canvas architecture.
8. **Dependency choice: vanilla WebGL2 first.** The GL surface is orthographic textured quads + two fragment shaders (+ at most one FBO pair) — roughly 300–400 lines of well-trodden infrastructure in a repo that currently ships zero extra dependencies. Named tripwires: adopt **OGL (~15KB)** if the effect roadmap grows into multi-pass render-target work; adopt three.js only if an actual 3D scene ever becomes the product.

## Why not the nearest alternatives

- **Per-card `<canvas>` per image** — 8 WebGL contexts today, right at typical browser context caps (oldest context gets killed), N render loops, cost grows with the grid, and the open transition is clipped to the card's box. This is the classic first-draft mistake the shared canvas exists to fix.
- **React Three Fiber (+ drei)** — pulls three.js (~150KB min+gzip) plus a second reconciler to draw flat quads with custom fragment shaders: no camera motion, no lighting, no scene graph used. R3F earns its keep when the scene is the product; here GL is a cosmetic layer over DOM truth.
- **curtains.js** — the closest alternative, and it validates the pattern: it is exactly "DOM-synced WebGL planes." But it is a WebGL1-era library with sparse maintenance, taken on to avoid ~100 lines of sync code we can own and test. Copy its shape, skip the dependency.
- **SVG `feTurbulence`/`feDisplacementMap` or CSS filters** — zero-dependency, but below the "high-end" bar: no true refraction/chromatic dispersion or velocity-driven flow, filter rasterization happens on the main thread (janky when animated per-pointer-move), long-standing Safari performance/compat pitfalls, and `backdrop-filter: url(#…)` displacement is Chromium-only. Right tool for a subtle wobble, not this brief.
- **View Transitions API / Motion for the open transition** — snapshot crossfade + transforms only; cannot produce a shader-like dissolve/refraction. Worth keeping in the back pocket as the *no-WebGL* open-transition fallback if "open" becomes route navigation (Next 16 supports it experimentally), not as the primary.
- **WebGPU** — unnecessary for this effect class; WebGL2 is the universal baseline in 2026, and isolating the renderer module keeps a future backend swap cheap.

## Risks and the one pending decision

- **Scroll/resize "swim"** (GL plane lagging its DOM rect) is the main quality risk of this architecture. Mitigation is standard: re-measure rects only on ResizeObserver/mutation, read scroll offset inside the same RAF that draws, keep the transform math in one module.
- **Placeholder-vs-image duality**: bind everything to the `data-project-media` contract so the gradient-to-`<img>` swap later is a texture-path change, not an architecture change.
- **Color parity**: GL and DOM can decode/gamma-handle the same image slightly differently; verified cheaply because the enter-frame draws the undistorted texture over the live image.
- **Context loss**: handle `webglcontextlost` by hiding the canvas — the DOM beneath is always complete.
- **Pending decision (owner input needed eventually, not blocking):** what "open" navigates to. Overlay/dialog → island lives in `app/page.jsx`; a future `/projects/[id]` route with cross-page continuity → island moves to `app/layout.jsx` so the shared canvas persists through navigation and can carry the transition into the detail hero. The architecture is identical either way; only the mount point moves.
