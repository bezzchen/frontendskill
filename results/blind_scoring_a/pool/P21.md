## What the repository actually is

- **Stack:** Next 16.2.12 (App Router, no `next.config` → Turbopack defaults), React 19.2.8, Tailwind 4.3.3. **No other dependencies.** The only client JS today is `SettingsPanel`.
- **`/components/ProjectGrid.jsx`** is a Server Component. Each card is a plain `<a href="#project-N">` with an `<h3>`, a `<p>`, and — critically — the "media" is a **decorative gradient `<div aria-hidden data-project-media>`**, not an `<img>`. There are no image assets and no `public/` directory.
- **The `#project-N` anchors have no targets** and there is no detail route. "Opened" currently means nothing in the DOM.
- `/components/ConstellationData.js` (500 items) is imported by nothing — irrelevant to this work.

Two things therefore have to exist regardless of architecture: real `<img>` elements (they are both the texture source and the thing that keeps SEO/a11y/responsive behaviour ordinary), and a definition of what "open" navigates to. Assumption I'm making so the design isn't blocked: the transition is a **destination-agnostic departure animation** that runs before/through navigation, whether the destination becomes a `/projects/[id]` route or stays an in-page target.

## Register: W (Expressive) with a scoped media layer — spectacle weighed and declined as a page register

The brief's language ("high-end", "dramatic", "shader-like") is a spectacle signal, so I weighed S explicitly. Full S would mean the grid itself is rendered in GL with the DOM demoted to hidden proxies. Rejected: it contradicts the brief's normal-DOM requirement and makes two systems own layout. What the brief actually describes is one signature idea (refractive images, one transition) on a page that is otherwise Q (the settings form). The GL substrate is spectacle-grade but confined to the media surfaces; it must be inert everywhere else.

## Recommendation: one shared, route-persistent WebGL2 media layer synced to the real `<img>` rects

A single `position: fixed; inset: 0; pointer-events: none` canvas, mounted once from `app/layout.jsx`, draws one textured quad per **visible** project image at exactly that image's `getBoundingClientRect()`, using the `<img>` element itself as the texture. The DOM keeps owning layout, links, focus, text, and responsiveness; the canvas owns pixels only. Hand-built in raw WebGL2 (~300 lines plus two fragment shaders), **zero new dependencies**.

**Boundaries (one owner per concern):**

| Piece | Owns |
|---|---|
| `components/gl/liquid-engine.js` (framework-free) | context + DPR/resize, 2 programs, textures, rect sync, loop policy, context loss. API: `register(img) → handle`, `pointer(handle,u,v)`, `open(handle) → Promise`, `release()`, `destroy()` |
| `components/gl/LiquidLayer.jsx` (`"use client"`, in root layout) | renders `<canvas aria-hidden>`; creates the engine lazily on first registration; gates on WebGL2 + `prefers-reduced-motion: no-preference`; sets `data-gl="on"` on `<html>` so CSS hides the `<img>`s (`visibility: hidden`) only once textures are ready |
| `components/ProjectCard.jsx` (`"use client"`, still SSR'd — identical HTML) | `<a>` + `<img>` + `<h3>` + `<p>`; registers the img ref; pointer handlers → UV → engine; click: unmodified click and engine active → `preventDefault`, `await engine.open()`, navigate, `release()`; otherwise native |
| `ProjectGrid.jsx` | stays a Server Component mapping data → cards |
| Shaders | JS template strings (no Turbopack loader config) |

**Pixel pipeline.** Texture uploaded from the `<img>` after decode (re-upload if `currentSrc` changes via `srcset`); quad drawn with `object-fit: cover` UV math and an SDF rounded-corner mask matching `rounded-lg`. The canvas sits **above** the cards (they have opaque `--surface` backgrounds, so a below-content canvas would be hidden), transparent everywhere except the image rects.

**Pointer effect.** Analytic refraction from a uniform ring buffer (≤12 recent pointer samples: uv, birth time, velocity) — summed ring gradients give a normal → uv offset, three-tap chromatic dispersion, specular. No state texture, no FBO simulation, no per-frame CPU→GPU upload; it is a pure function of (uniforms, time), which is what makes it pausable.

**Open transition.** A "cover": the quad rect lerps tile → viewport while `open.frag` runs (noise-displaced refraction scaled by `sin(pπ)`, dispersion, corner radius → 0), ending opaque; navigation happens under it; the layer fades out over the new route, with a timeout guard. Because the layer lives in the root layout it survives client navigation. Upgrading later to a true shared-element handoff (register the destination hero as a second texture) changes no architecture.

**Loop policy (constraint).** Render-on-demand: a rAF is pending only while (pointer active ∨ ripple energy > ε ∨ transition playing ∨ scroll/resize/texture-load dirty flag) ∧ grid intersects the viewport (IntersectionObserver) ∧ `document.visibilityState === "visible"`. At rest: nothing scheduled. Scroll redraws exactly one frame (rects moved). DPR capped at 2, `antialias: false`, `powerPreference: "low-power"`, textures ≤ 2048 with mips.

**Fallbacks.** No WebGL2 / reduced motion / context lost → `data-gl` off → plain `<img>`s and native links. Touch (`hover: none`) → no pointer effect, transition still plays on tap and on Enter (keyboard fires the same click handler). Modifier/middle clicks → native new-tab behaviour, no transition. Images are decorative (`alt=""`, the card has an `<h3>`); if alt ever becomes meaningful, hide via `opacity: 0` instead of `visibility: hidden` to keep AT exposure.

**Verification I will do under the real conditions, not proxies:** an instrumented rAF counter must read 0 over 2 s when (a) the grid is actually scrolled offscreen, (b) the tab is hidden, (c) the pointer has been at rest for >1.5 s with the grid visible; plus modifier-click opens a new tab with no transition, LCP still attributes to the `<img>`, and a screenshot diff between `data-gl` on/off at rest is below threshold.

## Why this beats the nearest alternatives

1. **Per-tile canvas/context** (adopting React Bits `GridDistortion`, or Paper Shaders `Water`/`LensDistortion` per card): N contexts — Chrome evicts the oldest past ~16, so a grid that grows breaks — N program compiles, and no way for the open transition to escape the tile without a *second* rendering system. `GridDistortion` specifically (source verified today): hard `three.js` dependency, one `WebGLRenderer` per instance, unconditional rAF with no IO/visibility pause, `mousemove` only, plain displacement with no dispersion or specular. Paper Shaders (0.0.80, published today): none of its image shaders exposes a pointer uniform. **Fit gate: both reference-only** — GridDistortion's velocity-injected displacement grid is a legitimate alternative look if the director prefers "stretch" over "water"; Paper's lens-distortion dispersion chain and its IO + `visibilitychange` pause pattern are worth copying.
2. **three.js / R3F + drei `<View>`** (r185, fiber 9.7, drei 10.7): ~150 kB gz plus a reconciler to draw eight quads and two shaders; the rect sync would still be ours; monthly API churn. The substrate would own nothing we need.
3. **OGL** (1.0.11, last published Jan 2025): the honest one-notch-up option — same architecture, GLSL passthrough, saves ~80 lines of boilerplate. Sanctioned swap if the implementer wants a wrapper; not the default because it buys little for a dependency nobody is upkeeping.
4. **curtains.js** (8.1.6, last published May 2024): literally this architecture as a library, but dormant — its author moved to `gpu-curtains` (WebGPU-first, 0.16). WebGPU coverage is still not universal and two fragment shaders gain nothing from it.
5. **Pixi.js `DisplacementFilter`** (8.20): the canonical liquid primitive, but a full 2D scene graph for eight sprites, a shared ticker that runs by default (the exact hazard the guidance names), and the transition would still be a custom filter. Reference-only.
6. **CSS/SVG filters** (`feDisplacementMap`/`feTurbulence`, backdrop-filter "liquid glass"): zero deps but CPU-rasterised per frame on large bitmaps (Safari worst), no controllable dispersion or specular, and no shader-like transition. Not even a good fallback — the fallback is the untouched `<img>`.
7. **View Transitions API** (Next 16 experimental / React `<ViewTransition>`): right tool for a layout morph, wrong for a shader — it animates snapshots, no GLSL on the pseudo-elements. Running it on the same element as the GL cover would be two engines owning one transform. Keep it off the media; fine for other routes later.

## What remains the design director's, not mine

Ripple radius/decay, dispersion amount, specular, transition choreography (duration, easing, dissolve to colour vs. destination image), whether corners stay rounded, whether touch gets a tap ripple. The only constraint I impose: every effect stays a pure function of (uniforms, time) so the loop can stop.

Real image assets and `<img>` markup don't exist yet; the "open" destination is undefined (the cover works either way); a z-index tier for the layer relative to future overlays should be a CSS variable.
