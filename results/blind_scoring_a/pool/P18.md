One **technique** is adopted from Motion's source: `pathLength="1"` with *unitless* `stroke-dasharray`/`stroke-dashoffset` (px values are mis-scaled by Safari page zoom — motion#3301).

## The architecture: one layout primitive, one scalar, one owner each

1. **Hold and release — CSS `position: sticky`.** The section root contains a tall `track` (`height: 100svh + 3 × 100svh`) holding a `stage` (`position: sticky; top: 0; height: 100svh`). The stage holds for exactly 300svh of scrolling and releases the moment the track's bottom meets the stage's bottom — a layout fact, so the release needs no JS, produces no layout shift, and the page's `scrollHeight` is constant throughout. No pin-spacer, no `position: fixed`, no scroll-jacking, no smooth-scroll library, no scroll-snap (snapping would fight the natural release).

2. **Progress — one JS-owned number.** A hook `useScrollChoreography(trackRef, stageRef)` computes `p = clamp(-track.getBoundingClientRect().top / range, 0, 1)` where `range = track.offsetHeight − stage.offsetHeight` (cached via `ResizeObserver`, so it is correct under mobile toolbar resizes). `p` is written as `--progress` on the section root with `style.setProperty` — never React state — so **no React re-render occurs per scroll frame.** The listener is `passive`, coalesced to one `requestAnimationFrame` per burst, and attached **only while an `IntersectionObserver` says the track is near the viewport**; on leave it detaches after one terminal write (0 or 1). There is no ambient loop anywhere in this design, so constraint 1 is satisfied by construction; a `visibilitychange → visible` resync is the only extra.

3. **Choreography — pure CSS functions of `--progress`.** Every act carries `--in`/`--out` (inline from data) and every slot carries `--delay`; the CSS module derives act entrance `--a`, act exit `--x`, and slot time `--t`, then `opacity: var(--t); translate: 0 calc((1 − var(--t)) × 1.5rem)`. Scrubbing backwards works for free, the sequence is deterministic, and timing lives in one constants object. Acts stack in a single grid cell of the stage; inactive acts get `pointer-events: none`.

4. **The drawn path — a decorative spine.** One `aria-hidden` SVG overlay on the stage with one `<path pathLength="1">`, `stroke-dasharray: 1 1; stroke-dashoffset: calc(1 − var(--progress))`. Its geometry is authored so its thirds land on the three acts; the design director may instead bind it into the diagrams — same mechanism.

5. **Static by default; choreography is opt-in.** The base CSS renders all three acts stacked, fully visible, path fully drawn. The client shell sets `data-choreo="on"` on the section root in a `useLayoutEffect` (React 19 removed the SSR warning) only when `!prefers-reduced-motion && viewport ≥ 40rem × 35rem`, both via live `matchMedia` listeners. Consequently SSR, no-JS, reduced-motion, and small-viewport users all get the identical DOM and content with no 300svh void — reduced motion is not a second component tree, it is the default one.

6. **Component boundary — children composition.** `CaseStudy.jsx` (server) renders all content: `<h2>`, three `<article>` acts with `<h3>`, prose, inline-SVG `<figure role="img">` diagrams, and `<figure>` media using the existing `data-project-media` placeholder convention (swap to `next/image` when assets exist). It passes them as `children` into `ScrollStage.jsx` (client, ~60 lines): the refs, the hook, the `data-choreo` flag, and the act indicator (`<ol>` with `aria-current="step"`, driven by the hook's *discrete* `activeAct` state, which changes three times per pass). Content never re-renders during scroll. Both files import one `CaseStudy.module.css` (supported in server and client components under Turbopack; I avoid `composes`/`:global`, which Lightning CSS lacks).

**Staging grammar** (director tunes, architecture supports): each act has the same three slots — typography, diagram, media — with a rotating lead: Act I *Problem* is type-led, Act II *Approach* is diagram-led, Act III *Outcome* is media-led. Windows: acts at 0–0.33 / 0.33–0.66 / 0.66–0.92, ~0.12 entrance with 0.04 stagger, ~0.05 crossfade exits, and a 0.92–1.0 settle so Act III is static when sticky releases into the settings section. One CTA link lives in normal flow *below* the track, so **no focusable element sits inside the acts** — opacity-hidden acts stay in the accessibility tree (screen readers read the case study linearly) without trapping keyboard focus.

## Risks and trade-offs, stated up front

- **Hydration relayout:** the static→track flip grows `scrollHeight` by ~300svh at hydration. The section is below the fold so it is invisible in practice; if measured CLS ever shows it, the fix is a synchronous inline gate script (theme-script pattern), deliberately not in v1.
- **Safari one-frame lag:** async scrolling can put JS-driven opacity one frame behind; the sticky hold itself is compositor-driven and stays exact. Imperceptible for fades; if it isn't, the SDA enhancement is the remedy.
- **Sticky killers:** any future `overflow-x: hidden` on `body`/`main` breaks the hold; use `overflow-x: clip` instead. I'll leave a comment at the track.
- **Mobile:** below 40rem × 35rem three slots can't fit a `100svh` stage at readable sizes, so those users get the static layout by design (same content).
- **`@property --progress`** is optional hardening (Firefox ≥128); unset `--progress` degrades to visible content, never to a hidden stage.

1. Hold: at five scroll positions inside the track, `stage.getBoundingClientRect().top === 0`.
2. Tracking: `--progress` equals `(scrollY − trackTop)/range` ±0.005 and is monotonic; spine `stroke-dashoffset` equals `1 − p`.
3. Stages: inside Act II's entrance window, diagram opacity ≥ type ≥ media (rotated lead); crossfade windows show Act I falling while Act II rises.

6. No-JS and `next build` HTML: all three acts present and visible.
7. Listener gating via CDP `getEventListeners(window)`: zero of ours at page top, ≥1 inside the track, zero again after scrolling past — the real scroll condition, not a `document.hidden` proxy.
8. Viewport gate: 375×667 static, 1280×800 choreographed; light and dark palettes; no hydration or React warnings in console; Tab order never enters the stage.
