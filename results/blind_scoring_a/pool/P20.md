## Proposed architecture

**Core decision: zero-dependency sticky-track scroll engine, built as progressive enhancement.** A tall scroll "track" (~400vh) wraps a `position: sticky; top: 0; height: 100svh` stage. Native scrolling is never intercepted — no wheel handlers, no scroll-jacking — so the pin holds for exactly the track's height and then releases into normal flow by construction. Scroll position maps to a single normalized progress value (0–1) that drives everything.

**Why not a library:** the repo has zero animation deps and the brief says the rest of the site stays ordinary React/Next.js. One section doesn't justify framer-motion (~30kb) or GSAP ScrollTrigger. Pure CSS scroll-driven animations (`animation-timeline: scroll()`) were considered but rejected as the primary mechanism: Safari support is too recent to rely on alone, and we need JS anyway for act-threshold logic. A small rAF-based engine (~80 lines) is fully controllable and testable.

### The scroll engine (`useScrollTimeline`)

- **Progress model:** `progress = clamp((-trackRect.top) / (trackHeight - viewportHeight), 0, 1)`, computed in a rAF loop gated by an IntersectionObserver (engine only runs while the track is near the viewport). Passive listeners; metrics cached and refreshed by ResizeObserver + window resize.
- **Two classes of motion, routed differently:**
  1. **Scrubbed (continuous)** — written every frame as CSS custom properties on the track node via `style.setProperty` (`--p` overall, plus per-segment remapped vars like `--path-p`). **Never enters React state** — zero re-renders during scroll, consumed by CSS `calc()`. Drives the SVG draw, rail fill, and any media crossfade/parallax.
  2. **Staged (discrete)** — an act timeline over the 0–1 domain (roughly Act I 0–0.30, Act II 0.30–0.62, Act III 0.62–0.92, release ramp 0.92–1.0). Crossing a threshold writes `data-act="n"` on the stage (DOM attribute, not React state). CSS attribute selectors + transitions with per-element `transition-delay` produce the coordinated typography → diagram → media stagger within each act. Reversible: scrolling back re-runs stages in reverse. Hidden stages use `opacity` + `visibility` transitions so off-stage content is neither readable by AT mid-choreography nor focusable.
- **Mid-page loads / anchor jumps:** progress computed immediately on mount from the current scroll offset, so reloading mid-track or arriving via anchor renders the correct state.

### SVG path drawing (`StoryPath`)

The connective spine across the three acts. The `<path>` gets `pathLength="1"`, so `stroke-dasharray: 1` and `stroke-dashoffset: calc(1 - var(--path-p))` draw it with **no `getTotalLength()` measurement, no hydration mismatch, no layout read**. Milestone nodes at act boundaries fill when passed (same `data-act` selectors). Stroke uses `var(--foreground)`/`var(--muted)` so both themes work for free.

### Release mechanics

Nothing to build — it falls out of the sticky-track choice. When the scroller passes the end of the track, the sticky stage scrolls away like any block element and Account settings arrives normally. The final 8% of the timeline is a "settle" ramp (path complete, all stages resting) so the release doesn't cut mid-motion. Keyboard scrolling, spacebar, Page Down, find-in-page, and the native scrollbar all behave because scroll is never hijacked.

### Reduced motion, no-JS, and SSR (one mechanism for all three)

**Base CSS = the static layout.** Server render shows all three acts stacked, fully visible, track at `height: auto`, sticky off, path fully drawn. All choreography lives behind `@media (prefers-reduced-motion: no-preference)` **and** a `data-enhanced` attribute the client controller adds only after mount when `matchMedia('(prefers-reduced-motion: reduce)')` is false and the viewport is tall enough (`min-height` guard, ~480px, so short landscape phones also get the static layout). Consequences:

- Reduced-motion users get identical content, same DOM order, no pinning, no listeners attached (the hook checks the media query and stays inert; it also reacts to live toggles).
- No-JS and pre-hydration visitors get readable, indexable content — no flash of hidden text.
- Screen-reader users always have the real heading/article structure regardless of visual choreography.

### Accessibility and performance notes

- Section is a real `<section aria-labelledby>` with an `<h2>` and three `<article>`s (or an `<ol>` of acts) — the narrative is document structure, not divs with styles.
- `ProgressRail` is `aria-hidden` (purely decorative; the acts themselves are the semantic sequence).
- Animate only `transform`/`opacity` (+ the dashoffset); `will-change` applied only while the stage is pinned; one rAF loop, one style write target, no per-frame layout reads.
- Media follows the existing gradient-placeholder pattern (fixed aspect boxes) so no CLS.
