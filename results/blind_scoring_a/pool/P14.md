## Architecture proposal

### Decision 1 — No new dependencies; native sticky pinning, no scroll hijacking

The pin is CSS `position: sticky`, not GSAP/Framer/Lenis and not wheel-event interception:

- A tall **track** section (`~420vh`) contains a **stage** that is `sticky; top: 0; height: 100dvh`. While the track passes through the viewport the stage holds; when the track ends the stage scrolls away with normal document flow. That is requirement 5 ("release naturally") for free — no unpin math, no fixed/absolute swapping, no layout jump.
- Native scrolling stays untouched, so keyboard paging, scrollbar dragging, fragment jumps, and browser find-in-page all keep working. This is also the a11y-safe choice.
- The repo has zero deps and the whole engine is ~150 lines of hook code; a library would buy nothing but bundle weight and version churn. (CSS-only `animation-timeline: scroll()` was considered and rejected as the primary mechanism — Firefox support is still not reliable — though the design leaves room to layer it in later.)

### Decision 2 — One scroll-progress source, two write channels (the render-discipline core)

A single client hook computes narrative progress `p ∈ [0,1]` from the track's bounding rect: `p = clamp(-rect.top / (trackHeight - viewportHeight), 0, 1)`.

- **Activation**: an IntersectionObserver on the track starts/stops a rAF-coalesced scroll listener, so the page costs nothing while the section is off-screen.
- **Continuous channel (no React renders)**: each frame writes `--progress` (and a derived `--path-draw`) as CSS custom properties on the section root via ref, skipping writes when the rounded value is unchanged. The SVG path draw and the progress rail consume these. React never re-renders per scroll frame.
- **Discrete channel (rare renders)**: a pure function maps `p` to `{ actIndex, stageFlags }`; `setState` fires only when those change (a handful of times per traversal). Discrete state lands in the DOM as `data-act="2"` / `data-stage-media="in"` attributes.

### Decision 3 — Staged entrances = data attributes + CSS transitions, driven by a declarative timeline

Requirement 2 ("typography, diagrams, media enter in coordinated stages") and 3 ("sequence tracks scroll progress") are met by a **config-as-data timeline**, not imperative tweens:

```js
// caseStudyContent.js (shape sketch)
acts: [
  { id: "act-1", range: [0.04, 0.34],
    stages: { heading: 0.05, body: 0.30, diagram: 0.45, media: 0.65 } }, // act-local fractions
  ...
]
```

Pure functions in `timeline.js` turn global `p` into act-local progress and per-stage in/out booleans. Crossing a threshold toggles a data attribute; CSS transitions (opacity + small translate/clip) do the actual tweening. Because the mapping is pure and scrub-bound, scrolling backwards reverses every state deterministically — the sequence *tracks* scroll rather than autoplaying on entry, and fast scrolling never leaves orphaned mid-tween state (CSS transitions always settle toward the current attribute state). `timeline.js` is dependency-free and unit-testable.

Zone layout across `p` (three acts plus buffers so pin and release never cut a beat mid-flight):

```
0.00–0.04  lead-in: act 1 composes as the pin engages
0.04–0.34  ACT I   (problem/brief)
0.34–0.64  ACT II  (process/exploration)
0.64–0.92  ACT III (outcome/impact)
0.92–1.00  settle: fully-composed final frame; sticky releases into next section
```

### Decision 4 — SVG path draw via `pathLength="1"` + CSS variable

The connective spine (requirement 4) is one `<path pathLength="1">` in a decorative process diagram, with `stroke-dasharray: 1; stroke-dashoffset: calc(1 - var(--path-draw))`. The hook writes `--path-draw` (eased, 0→1 across the whole narrative) once per frame on the section root — one cheap paint of a single stroke, no per-frame React, no getTotalLength() measurement. Act waypoint nodes along the path light up via the same discrete data attributes. The SVG is `aria-hidden` decorative; stroke colors come from the existing `--foreground`/`--muted` tokens so dark mode works untouched.

### Decision 5 — Reduced motion and no-JS: same content, flow layout, zero choreography

Content-first, choreography-as-enhancement, enforced in three layers:

1. **Server HTML is the complete article.** All acts render as normal flowing semantic content (`section > h3 + p + figure`); nothing is hidden at SSR time.
2. **Choreography opts in, never out.** The pinned layout (tall track, sticky stage, absolutely-stacked act panels, pre-entrance hidden states) applies only under `[data-choreo="on"]`, an attribute set from a client effect **only when** `matchMedia("(prefers-reduced-motion: no-preference)")` matches. Reduced-motion users and no-JS users therefore get the identical content as an ordinary scrolling section — track height auto, no sticky, everything visible, SVG path fully drawn (`--path-draw` defaults to 1) — because the choreographed state is never applied, not because it's undone.
3. **CSS belt-and-braces**: `@media (prefers-reduced-motion: reduce)` additionally neutralizes transitions inside the section, and a `usePrefersReducedMotion` hook (with change listener) skips attaching observers/listeners entirely mid-session if the OS setting flips.

### Semantics and accessibility

- `<section aria-labelledby>` with `h2` (matching the page's existing h1→h2→h3 hierarchy); acts are `h3` blocks in DOM order = narrative order.
- In choreographed mode, inactive stacked act panels get `visibility: hidden` (transitioned) + `inert`, so screen readers and tab order only meet the active act; in flow mode everything is plainly visible.
- No focusable controls inside the decorative layers; rail and SVG are `aria-hidden`.
- `100dvh` for the stage (mobile URL-bar churn), and a `@media (max-height: 480px)` escape hatch that falls back to flow layout on very short viewports.

### Performance notes

- No ancestor of the sticky element may get `overflow: hidden` (breaks sticky) — only the stage itself clips its decorative layers; `body`/`main` are already clean.
- Transitions restricted to `opacity`/`transform`/`clip-path`; `will-change` only on the handful of currently-staging elements; no large blurs.
- Media uses the repo's existing gradient-placeholder aesthetic (`data-project-media`) — no next/image adoption in this change, consistent with `ProjectGrid`.

### Risks and verification plan (for the implementation pass)

- Unit-style checks on `timeline.js` (monotonicity, boundary exactness at 0/1, reversibility) can run under plain `node` since the repo has no test runner.
- Manual matrix: reduced-motion on/off (macOS toggle), no-JS, dark mode, keyboard PageDown through the track, `#project-1` fragment jump, short viewport, fast flick-scroll both directions.
- Known trap to watch: React 19 hydration warnings if `data-choreo` were set during render — it must be applied in an effect, which is already the design.
