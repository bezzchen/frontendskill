# Proposal: "Experience system" as a living, draggable, re-arrangeable DOM system

## 0. Summary

- **Register W (Expressive).** Spectacle (canvas/WebGL orbit) was weighed and declined: the orbiting objects are semantic content (focusable buttons that must reflow into a real CSS grid), so a graphical-system core would need a shadow DOM and two sources of truth.
- **Single engine: the anime.js 4.5.0 already installed.** No new dependency. Adopt four first-party modules that are already in the pinned package: `createDraggable` (drag + spring release, touch built in), `createLayout` (FLIP between arrangements, handles DOM reorder and transformed elements), `createScope` with `mediaQueries` (responsive teardown/re-setup), `createTimer` on the shared engine loop (orbit), plus `engine.pauseOnDocumentHidden` (default `true`, verified).
- **One system, two layout modes, three arrangements.** The same seven DOM nodes (six cards + one central "core") exist in every state. Field mode (orbit) is progressive enhancement for large screens with motion allowed; the structured CSS grid is the SSR baseline, the small-screen state, and the reduced-motion state.
- **Strict transform ownership.** Per element, each of `left/top`, `transform`, `translate` has exactly one writer at any moment (matrix in 5.3). This is the rule that makes orbit + drag + FLIP coexist without fighting.
- **Catalogs: nothing adoptable as code.** Every orbit/drag/layout component found (React Bits, Fancy Components, SmoothUI, Magic UI, Aceternity) is built on Motion, GSAP, three.js, matter-js, or pure CSS keyframes on the same node; all are reference-only.

## 3. Register decision

- **S (Spectacle) — weighed, declined.** The brief's "living system" points here, and 4.5.0 could even drive three.js. But the objects are the content: company/project names that must be keyboard-focusable, screen-reader-listed, tappable, and must become a clean readable grid on phones and on the tab switch. A canvas/WebGL system would need a parallel accessible DOM and would turn "same elements reorganize" into a two-world synchronization problem. Interaction (drag, tab) acts on discrete objects, which DOM does natively. Not chosen.
- **Q (Quiet) — rejected.** The brief explicitly asks for continuous ambient motion and drag; Q forbids both.
- **W (Expressive) — chosen.** One signature idea: *six real cards are one system with two phases — a loose orbital field and a structured grid — that the user can perturb and that re-organizes itself.* Orbit, drag, and re-arrangement are all expressions of that single idea; nothing else animates in the section.

## 5. Architecture

### 5.1 System model
- **Data**: the existing `items[]`, extended with `order`/`period` (sort key for structured mode), `summary` (shown in the core), `ring` (0 inner / 1 outer), `featured` (default core content).
- **Arrangements** (React state, one value): `overview` (orbit), `experience`, `projects`. A segmented control offers all three on large screens and only the last two on small screens.
- **Layout modes** (derived, not stored): `field` = large screen AND motion allowed AND arrangement `overview`; otherwise `structured`.
- Transitions between any two arrangements move the same nodes; nothing unmounts.

### 5.2 DOM and SSR baseline
- `section` → header + segmented control → `stage` (the layout root) containing: `core` (one element, stage center in field mode; the arrangement's header/summary cell in structured mode), six `card` buttons, and an optional decorative `<svg>` tether layer (outside the layout children set; SVG is excluded by the layout module anyway).
- Server HTML renders the structured grid for the default arrangement, so first paint, no-JS, and crawlers get the clean state. Field mode is applied post-hydration inside the scope; the very first entry into field mode reuses the structured→field transition as the section's entrance ("the grid lifts into orbit").
- Stage height is fixed on large screens (e.g. `clamp(480px, 62vh, 720px)`), and the structured grid is centered inside the same box, so arrangement switches never shift content below the section. On small screens the grid takes its natural height.
- React manages `className`, `data-*`, order (keys), and ARIA only — never the `style` prop on stage children, which belongs to anime.js.

### 5.3 Ownership matrix — one writer per property

| Element / property | Field mode | During an arrangement transition | Structured mode |
|---|---|---|---|
| card `left/top` | orbit timer (per frame) | layout module (recorded, forced during, restored after) | irrelevant (grid child, static) |
| card `transform` | draggable only (`translateX/Y`); zero when idle | none — draggables reverted and inline transform removed *before* `record()` | none |
| card `translate` | none | layout module (WAAPI) | none |
| core position | CSS (absolute center) | layout module | CSS grid area |
| card look (lift, shadow, dim) | CSS classes toggled from draggable callbacks / React | CSS | CSS |

Why orbit writes `left/top` on the card itself rather than `transform` on a wrapper: the draggable caches the inverse of its *ancestors'* transforms once and measures bounds with ancestor transforms muted, so a per-frame-transformed parent would give it stale, wrong bounds (flagged from source; see spike S2). With the orbit on the card's own `left/top`, the draggable's bounds are measured from the card's real rect at grab time, and the layout module records/restores `left/top` natively. Cost: layout work for six absolutely positioned elements inside a `contain: layout` stage — negligible; if profiling ever disagrees, the compositor-only variant is to write the `translate` property instead and bake it into `left/top` before each `record()`.

### 5.4 Orbit model (pure JS, no DOM)
- Per card: `theta`, `radius` (normalized to stage), `omega` (one revolution per ~90–120 s, ±15% per ring, rings counter-rotating), two low-frequency incommensurate sines on radius (±4%) and angle (±0.05 rad) seeded per card with `utils.createSeededRandom` for a deterministic organic drift, `frozen` flag, `targetTheta` for relaxation.
- Ring radii derived from stage size and card size so cards never overlap or leave the stage; elliptical squash from the stage aspect ratio; radius clamped to [0.35, 0.95] of the half-stage minus half-card.
- Gentle neighbor relaxation per ring: angles ease toward equal spacing with a weak damping (`utils.damp`), only for unfrozen cards, converging in ~2–3 s. This is what repairs bunching after the user drags cards together and gives the "living" quality without a physics engine.
- `step(dt)` is time-based (engine delta), so it is frame-rate independent; output is positions written with `utils.set(card, { left, top })` — no layout reads inside the loop.

### 5.5 Drag lifecycle (field mode only)
- One `createDraggable` per card: `container: stage`, small `containerPadding`, `containerFriction ≈ .85`, `releaseContainerFriction ≈ .9`, spring release, `maxVelocity ≈ 40`, `dragThreshold: { mouse: 3, touch: 8 }`, grab/grabbing cursors on fine pointers.
- `onGrab`: freeze that card's orbit parameters (the others keep moving), add `is-grabbed` class (lift via CSS), set it as the core's active item.
- release → library spring/inertia within the stage → `onSettle`: **absorb** — convert the card's visual center to polar coordinates, store as its new `theta/radius` (radius kept where the user left it; angle subject to gentle relaxation), then in the same frame write the new `left/top` and `draggable.reset()` (x/y to 0 with callbacks muted) so nothing jumps; unfreeze.
- Tap vs drag: the built-in threshold sets `dragged`; the button's `onClick` ignores the click if a drag occurred in that pointer sequence; otherwise it runs the card's primary action (activate in core / open).
- Keyboard parity: arrow keys on a focused card nudge `theta`/`radius`; Enter/Space is the primary action.
- Touch: the draggable sets `touch-action: none` on the six cards only; the stage and page still scroll. Field mode only exists at ≥1024 px, so on phones no content ever blocks scrolling (spike S3 covers tablets).

### 5.6 Arrangement transitions (layout module protocol)
1. Guard: if a card is grabbed or settling, `stop()` it and absorb immediately; set a `transitioning` flag that queues the latest requested arrangement.
2. Leaving field mode: pause the orbit timer; `revert()` the six draggables (removes their inline transforms and `touch-action`); ensure no inline `transform` remains on any card.
3. `layout.update(() => flushSync(() => setArrangement(next)))` — React commits the class change and keyed DOM reorder synchronously inside the callback, so `record()` sees the old state and `animate()` the new one. Fallback if `update()` misbehaves with React (the docs warn it may in some frameworks): `record()` in the handler, `setArrangement`, `animate()` in a `useLayoutEffect`.
4. Entering field mode: inside the same mutation callback, switch the stage to field mode and write each card's seed `left/top` (its remembered orbit position, so the user's arrangement survives a round-trip); the module FLIPs grid cells to those seeds. `onComplete`: create draggables, resume the timer (the seed equals what the loop computes at t₀, so motion continues seamlessly); restore focus to the card that had it before the DOM reorder.
5. Timing: ~600–700 ms, one ease, small stagger by target index — values are the director's call. Reduced motion: skip the module and commit instantly.

### 5.7 Responsive, touch, reduced-motion gating
- `createScope({ root: sectionRef, mediaQueries: { large: '(min-width: 64rem) and (min-height: 40rem)', reduceMotion: '(prefers-reduced-motion: reduce)', coarse: '(pointer: coarse)' } })`. The gate for field mode is **space and motion preference, not input type**: tablets in landscape get the orbit with touch drag; `coarse` only adjusts affordances (larger hit areas, a "drag to rearrange" hint instead of a cursor).
- On a media change the scope reverts timer, draggables, and layout and re-runs the constructor; the constructor's cleanup clears inline `left/top` so the CSS grid takes over cleanly, then reports `matches` to React so the derived mode updates.
- `prefers-reduced-motion`: structured only, all sizes; the segmented control still works, instantly.

### 5.8 Pause and performance architecture (constraint 1) and how it will be verified (constraint 2)
- Offscreen: an IntersectionObserver on the stage (`rootMargin` ≈ 10%) pauses/resumes the orbit timer; the anime-native alternative is `autoplay: onScroll({ target: stage, sync: 'play pause' })`. Hidden document: the engine's default pause covers the timer and any in-flight release springs. Structured mode: the timer is not running at all. Draggables are event-driven and cost nothing while idle.
- Per-frame cost: six trig evaluations and six `left/top` writes; no layout reads in the loop; `will-change` unnecessary.
- Verification under the exact conditions, using the dev server and the browser tools available here: scroll the section out of view and sample card positions over 500 ms (must be frozen), scroll back (must resume); open and front another tab to trigger a real `visibilitychange` and read an `onUpdate` counter before/after (no `document.hidden` stubbing); touch drag with the mobile/tablet emulation (real `touchstart/touchmove`); resize across 1024 px both ways and confirm no inline styles remain and the grid is clean; emulate reduced motion; confirm zero layout shift below the section during arrangement switches; verify a tap still fires the button and a drag does not.

### 5.9 Accessibility and semantics
- Cards stay `<button>`s inside a `role="group"` labelled by the section heading; the segmented control is a `radiogroup` (or `aria-pressed` buttons) labelled "Arrange".
- Structured mode: DOM order equals visual order because arrangement is a data sort committed through React keys (nodes move, never remount). Field mode: visual order is spatial and arbitrary, which is acceptable; reading order stays the data order.
- The core is `aria-live="polite"` but updated only from focus/tap, not hover, to avoid chatter. Focus is restored after reorders. Drag has a keyboard equivalent (5.5). All motion respects reduced motion.

## 6. Interaction model, by state and input

| | Overview / field (≥1024 px, motion allowed) | Experience or Projects / structured (all sizes) |
|---|---|---|
| Idle | Cards drift on two counter-rotating rings around the core; core shows the featured project. | Selected group in the primary rows in data order; other group parked in a compact secondary row; core is the arrangement header/summary. Nothing moves. |
| Hover / focus | Card lifts slightly (CSS); core shows that item; tether line (optional) brightens. | Standard focus ring; hover lift. |
| Pointer drag | Grab → card follows (slot frozen, others keep drifting) → release with inertia inside the stage → absorbed into its new orbit slot → ring gently re-spaces. | No drag (cards are plain buttons; reordering a grid is a different feature and would conflict with scrolling on touch). |
| Touch | Same as pointer on tablets; `touch-action: none` on cards only. | Tap only; page scrolls freely. |
| Tap / Enter / Space | Primary action (activate in core / open). | Same. |
| Arrow keys | Nudge the focused card's orbit angle/radius. | Move focus (native). |
| Segmented control | Overview → Experience/Projects: orbit pauses, cards FLIP into the grid (~650 ms, staggered). | Experience ↔ Projects: FLIP reorder within the grid; back to Overview: grid lifts into the remembered orbit. On small screens Overview is absent. |
| Scroll away / hide tab | Orbit pauses; resumes on return. | n/a |
